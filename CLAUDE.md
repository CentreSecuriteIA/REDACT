# REDACT — Red-team Dataset Automation & Construction Toolkit

## Project Overview

A modular, extensible pipeline for automated red teaming dataset generation. Built from lessons learned across multiple BELLS-O dataset iterations (content moderation input/output, jailbreaks). Designed to be reusable beyond red teaming — applicable to any synthetic data generation task.

The library generates, checks, filters, and stores samples across configurable harm categories. It is built to be model-agnostic (API or local vLLM), prompt-agnostic (prompts are external JSON files), and category-agnostic (a new category is a taxonomy entry). The product goal: a taxonomy and a task in, a dataset out, with defaults rather than settings.

Prompts and template files ship with the library. A `prompt_dir` overlays them file by file (`scripts/scaffold_prompts.py` writes an editable copy).

## Module Details

### Top level — `stages.py`, `recipe.py`, `driver.py`

A stage function (a **front**) may be called alone, from a notebook or a test; everything about a *run* (serving, residency, telemetry, run records, counting) lives in the driver, which reads what it needs about each stage from one table.

**Fronts** (`stages.py`): `generate_constitution`, `generate_inputs`, `generate_outputs`, `generate_jailbreaks`, `generate_paraphrases`, `build_dataset`. Each takes `data_dir` (the working root; every path derives from it through `paths.py`), a model name per role (`None` is the registry role's default), `prompt_dir`, `resume` (default `True`), `verbose`, `read_back`, and its own tunables. A front resolves its inputs (the frame given, else `dataset.merge_inputs(data_dir)`), its clients (`ModelClient.create`) and its output path (`paths.*(data_dir)` unless an `*_path` override is given), then calls its core: `ConstitutionPipeline.run`, `InputPipeline.run_from_constitution` or `run_standalone_inputs`, `run_output_generation`, `jailbreak.pipeline.run_augmentation` (once per augmentation kind), `run_paraphrase_target`, `dataset.write_concat`. The core owns the manifest, the ledger, `resume_state` and `CommitBuffer`, and returns the artifact's rows, or an empty frame with `read_back=False`. When the inputs a front resolves hold no accepted row (the run's were all rejected, or the frame given is empty), the outputs, jailbreak and paraphrase fronts log a WARNING, write nothing and return an empty frame, so a recipe run records 0 rows and goes on; with no inputs at all (no tree, no frame) `generate_outputs` and `generate_jailbreaks` raise `ValueError`. `generate_inputs` warns, with the counts, when it accepts under half of the samples it generated (`_LOW_ACCEPTANCE`). Two fronts differ: `generate_inputs` reads the seeded tree back with `merge_all` and writes `constitution_inputs_merged.csv`, the hand-off `build_dataset` reads; `generate_paraphrases` returns `{"inputs": df, "outputs": df}`.

**The `Stage` table**: `STAGES` maps each recipe stage name, in run order (`constitution`, `inputs`, `outputs`, `paraphrase`, `jailbreaks`, `build`), to a frozen `Stage(name, front, roles, files, recipe_kwargs)`: the front's name, looked up on `redact` when the stage runs (`Stage.run`); the `(recipe role, registry role)` pairs it calls; `files(ctx)`, the CSVs that hold its rows and the column values a counted row holds; and `recipe_kwargs(ctx)`, what the run passes the front from the recipe. `Stage.check(ctx)` raises for a params key the front does not take or one the run passes itself, reading no file, and `run_pipeline` calls it for every listed stage before the first runs; `Stage.kwargs(ctx)` then lays the checked params over the recipe kwargs. A recipe kwarg an earlier stage saves is a `Saved(read)`, read when its stage starts (the training run's constitution). `folded` names params keys the run applies to a kwarg it passes itself: the jailbreak stage's flat keywords, laid over the section's adversarial kind, so the front does not get them twice. `RunContext` is what one run hands its stages: `data_dir`, `dataset_type`, `models` (recipe role → name), `prompt_dir`, `taxonomy`, `taxonomy_dir`, `params`, `augmentations` (both kinds resolved), `resume`, `verbose`. A new stage is a front plus a row.

**Recipe** (`recipe.py`): `load_recipe(path | dict)` reads and checks the keys (an unknown top-level key raises; `_`-prefixed keys are comments): `dataset_type` (`"eval"`: standalone inputs, no constitution; `"training"`: inputs seeded from the constitution saved under `data_dir`, which must exist), `data_dir`, `stages` (default `["inputs", "outputs", "jailbreaks", "build"]`; `[]` runs nothing; an unknown or repeated name raises, so does `constitution` in an eval recipe), `models`, `taxonomy`/`taxonomy_dir`/`prompt_dir`, `augmentations` (resolved by `augmentations_of(recipe, params["jailbreaks"])`, see the jailbreak section; the loaded recipe holds it resolved), `params_file` (relative to the recipe) and `resume`. A role of `models` (`gen`, `check`, `translation`, `constitution`, `paraphraser`, `paraphrase_check`) is a registry name, `null` for the role's default, or an object `{name, backend_type, copies, workers}` that also says how the model is served; `serving_of` checks it against the registry (`copies` only for a vLLM setup, `workers` only for an API one) and one model is served one way per run. `load_params` reads the params file: each front's kwargs under its stage's name. `resolve_role` gives the models a role stands for, as its stage resolves them: `check` left out is `gen`'s model, `paraphraser` may be `"distribution"` (every paraphraser), and `translation` is no model when no augmentation kind draws a translation technique.

**Driver** (`driver.py`): `run_pipeline(recipe, params=None, verbose=True, data_dir=None)` builds the `RunContext`, checks the params, installs telemetry, logs the prompt overlay (`report_prompt_sources`), sets the run's serving (`capabilities.set_run_serving`) and plans residency per stage (`residency.plan_phases`; a plan that does not fit is logged, never fatal). Then, per stage: it enters the stage's phase (unloads the engines the stage's plan leaves out, preloads the stage's local models and the next stage's when they fit beside them), runs `stage.run(read_back=False, **stage.kwargs(ctx))` inside `telemetry.stage(name)`, counts rows from `stage.files(ctx)` (`file_counts`; no stage reads its rows back) and writes the run record `{data_dir}/Datasets/{stage}.run.json` (`write_record`: `stage`, `timestamp`, `params`, `models`, `counts`, `sources`, `serving`; the `jailbreaks` record adds `spec_version` and `augmentation`, the section the stage ran, params flat keywords applied). Its `finally` clears the serving, joins the preload threads, unloads every local engine and rolls telemetry up, after a failed stage too, without masking the stage's error. It returns `{dataset_type, data_dir, stages: {name: {counts, manifest}}, serving, telemetry}`, plus `residency` and `trace` when present; `"manifest"` there is the record's path, a key kept by that name. `scripts/run.py RECIPE [--params P] [--data-dir D] [--quiet|--debug]` is the CLI (it configures logging; SIGTERM exits through the `finally`, so engines are released); `scripts/inspect_run.py DATA_DIR` prints each record. `redact.pipelines`, `redact.runconfig` and the names `manifest_path`/`write_manifest`/`read_manifest` are aliases kept for one release.

**Package root**: `__init__.py` attaches a `NullHandler` to the `redact` logger and sets no level, loads `.env` from `get_output_dir()` (its values win over the shell's) before the subpackages import, and lists its re-exports in `__all__`. Importing seeds nothing; `set_seed(seed=42)` seeds `random` and `numpy` when the caller asks. `exceptions.py` holds `RedactError` and `PromptTooLongError(RedactError)`, which a backend raises for a prompt over the model's context (see `llm_pipeline/` below); elsewhere the library raises built-in errors.

### `llms/` — LLM Abstraction Layer

The core abstraction. Everything above this layer calls a unified interface and is backend-agnostic.

**Base class** (`backends/base.py`): a backend **is a configured model**, not a bare transport. Everything fixed about one registered model — its name, `default_max_tokens`/`default_temperature`, its system-prompt policy, its `rpm` and `max_workers`, its provider params, its sampling defaults — is bound once in `from_config()`/`__init__` and never re-passed. `generate(messages_list, *, max_tokens=None, temperature=None, internals_ids=None, **kwargs) -> list[str]` therefore takes only what genuinely varies per call: the messages (system text travels in them as system-role messages) and the two overrides that have real callers. A single sample is a batch of one; the one singular method is the coroutine `agenerate(messages, ...)`, present only on backends with `supports_async_calls`. Two shared helpers on the base do what `wrappers.resolve_call_params()` used to do upstream: `_prepare()` takes the system-role messages already in each list and splits them out or folds them into the first non-system message per `supports_system_prompt`, and `_resolve()` fills `max_tokens`/`temperature` from the model's stored defaults. `max_workers` is **clamped in `__init__`** against the class's own `supports_parallel_calls`, so the setup's `recommended_max_workers` and the transport's parallelism facts are reconciled exactly once — nothing downstream re-decides it. Capability facts live in one `compute_config` **ClassVar** holding a frozen `ComputeConfig(supports_native_batching, supports_parallel_calls, supports_internals, supports_async_calls)`; being a class attribute is what lets registration-time checks and `model_compute_config()` read them without constructing a transport (which for vLLM/introspection would load weights). These flags are how every layer above stays backend-agnostic: callers never branch on backend type, they read `compute_config`.

**Backends** (`backends/` — one file per provider, each implementing `LLMBackend` **and its own `from_config(config)`**, which reads that provider's setup off the registry entry; `capabilities.backend_for(config, setup)` is what calls it). Backend *instances* are per model and cheap; what they **use** may not be (an API backend holds its shared SDK client; a local backend holds only its engine's cache key and reads the engine from the cache on each `generate()`, so a backend never keeps a released engine alive), so each module caches its own expensive resource on that resource's own identity — and those caches are strictly **per class**: `openai.py`/`anthropic.py` share one SDK object (HTTP connection pool) per endpoint between the per-model backends using it, `vllm.py` caches the engine per `(hf_model_id, quantization, vllm_kwargs)` — which is what makes `venice-uncensored[vllm]` and `venice-paraphraser` share one load instead of loading the same checkpoint twice — and `introspection.py` keeps a *separate* cache keyed the same way, because a vLLM engine and a `transformers` model are different runtimes and the same `hf_model_id` means two independent loads. `clear_transport_caches()` resets all of them, shutting local engines down and freeing their memory; a client built on a released engine raises on its next call:
- `backends/openai.py` — `OpenAIBackend`: generic OpenAI-compatible API (uncensored hosted models); `generate()` fans out through `BatchCaller`, `agenerate()` runs on a cached async SDK client, so these models use the async lane too. Venice AI is the only provider currently registered against it — the class itself has no Venice-specific logic at all; the endpoint identity lives entirely in the registry entry's `APIConfig`.
- `backends/anthropic.py` — Claude via native SDK (system param split out); series-only
- `backends/vllm.py` — `VLLMBackend`: local inference on vLLM's `AsyncLLM`, run in this process (`supports_async_calls=True`). Every item is its own engine request, awaited on the shared loop of `llms/aio.py`, and the engine batches whatever is in flight: `agenerate()` makes one request, `generate()` one per item and blocks until all have answered (one failure cancels the rest). `max_workers` defaults to the engine's `max_num_seqs` times its copies: what the async lane keeps in flight. The engine loads with the residency plan's `gpu_memory_utilization` and cards (`set_planned_utilization`/`set_planned_devices`, both kept out of the cache key); planned cards beyond one copy's span become `data_parallel_size` copies inside one engine. `max_model_len` defaults to `estimate.effective_max_model_len()`. Prompts are tokenized with the engine tokenizer's chat template, so a checkpoint whose tokenizer ships a `chat_template` works as-is; for one that does not (Mistral-3.x), pass `tokenizer_mode="mistral"` through `vllm_kwargs`. A prompt longer than the context raises `PromptTooLongError` for its request alone, and a request aborted by a release raises instead of returning cut text. Each request is one telemetry `call` event. A leading `|>` artifact (ChatML tokens missing from the vocabulary) is stripped.
- `backends/introspection.py` — `TransformersIntrospectionBackend`: local raw-HF-`transformers` inference (not a vLLM extension — vLLM's continuous batching discards intermediate activations by design) for research/interpretability logging. Config-driven `capture` (`logprobs` / `hidden_states`: `False`/`"last"`/`"all"` / `attention`), defaulting to the lightest option (logprobs + last-layer hidden state) since attention scales `layers × heads × seq_len²` and there's no batching to amortize storage over. A setup that captures attention loads with `attn_implementation="eager"` (`IntrospectConfig.load_kwargs`) unless its `extra_kwargs` name one, and a capture replaces the files an earlier one left under the same id. Registered via `backend_type="introspect"` + `introspect=IntrospectConfig(hf_model_id=..., log_dir=..., capture={...})` — the type is named for the `.introspect` field holding its setup, matching how `"vllm"` names `.vllm`; `supports_native_batching=False`, `supports_parallel_calls=False`, `supports_internals=True`. Capture is opt-in per call: pass `internals_id` (single) / `internals_ids` (batch, one per item) — an id the *caller* computes and internals are written under `{log_dir}/{internals_id}/`; `backends/introspection.py` never interprets the id beyond that (no CSV columns, no ids of its own — see "Internals capture is a non-interfering hook" below). `ModelClient.generate()` is the enforcement point: it raises `ValueError` if `internals_ids` is passed to a transport with `supports_internals=False`, rather than letting it silently reach (and crash inside) e.g. the OpenAI/Anthropic SDK call. Its loaded-model cache is its own, never shared with vLLM's, since the same `hf_model_id` under `transformers` and under vLLM is two different runtimes. Every capture also gets an always-written `meta.json` alongside whatever tensors `capture` asks for — resolved model/settings, input messages, output text — self-contained for analysis, and the only place multi-round jailbreak techniques' discarded intermediate prompts/completions survive at all. `LLMBackend.rename_capture(old_id, new_id)` (default no-op, real move-the-folder implementation here) lets a caller capture under a pre-call-known **provisional** id and relabel it once a stage's real post-hoc identity (its `sample_id`) is known — needed wherever the resulting text's own hash isn't knowable before the call returns (paraphrase, jailbreak). Wired into `generate_outputs()` (`f"{input_id}/output"` / `.../val_out`, no rename needed — the row's identity is already `input_id`), `run_from_constitution` (`input`/`val_in`, gated to one sample per LLM call — see the design doc), paraphrase (`{input_id}/paraphrase/{sample_id}/`, provisional-then-renamed), and the jailbreak stage (`{input_id}/jailbreak/{sample_id}/{technique}/{n}/`, provisional-then-renamed; `chain._wrap` tags each request by that request's own model, so a chain mixing an internals-capable `gen_model` with a non-capable `translate_model` captures exactly what's capturable). Not yet wired: multi-turn conversations (subsystem itself still settling). Full design/status: `.claude/introspection_backend_plan.md`.

**`client.py`**: `ModelClient` is a **configured backend plus its dispatch strategy** — and the only thing callers pass around. The backend already knows *what* to call; the client adds the two things that turn "make one call" into "run a batch": a `RateLimiter` and, for transports without native batching, a `BatchCaller`. Which applies is read **once in `__init__`** off the backend's `compute_config` — never per call, and never from the registry: a native-batching transport gets the whole list handed to the engine unwrapped, everything else fans out through the `BatchCaller` (whose worker count the backend already clamped). Because of that, no call site threads a limiter, picks a dispatch mode, or branches on backend type. Build one with `ModelClient.create("venice-uncensored")`; from then on every client is used identically: `client.generate(messages_list) -> list[str]`, batch in, batch out. `create()` is four lines — resolve the setup, build the backend, wrap it — and there is deliberately **no client cache**: a client is microseconds to build, while everything expensive it reaches is already cached on that thing's own identity (SDK pools per endpoint, vLLM engines per checkpoint, rate-limit windows per key). Caching the wrapper on top bought nothing and cost correctness — the cached client held the only other reference to an engine, so `clear_transport_caches()` freed no GPU memory and a rotated API key never took effect. Two clients for one model still share one window, via `wrappers.shared_limiter`. There is deliberately **no `_validate()`**: the old client took `(backend, model, config, backend_type)` as four loose arguments and had to check they agreed; a backend built *from* the config cannot disagree with it, so the check has nothing left to catch. `api_config` is likewise gone — the budget lives on the backend, resolved from the setup it was actually built from. What the client deliberately does *not* do: resolve params, assemble messages, build checkers, or interpret accept/reject — those are the backend, `prompts.py`, `checker.py` and `llm_pipeline/check.py`.

**`model_config.py`**: `MODEL_REGISTRY` of `ModelConfig` entries. **Every config validates itself in `__post_init__`**, so anything in the registry is coherent by construction rather than by a downstream check. An identity (backend-agnostic: `name`, `role`, `is_uncensored`, `supports_system_prompt`, `default_max_tokens`, `default_temperature`) composes with per-backend-type setups you build yourself and pass in — `APIConfig` (`backend_type` naming the provider, `api_key_env`, `rpm` all required, plus `base_url` — required for `openai`, which serves any compatible endpoint — `api_model_id`, `rate_limit_scope`, `recommended_max_workers`, `default_extra_body`, `price_per_1m_input`/`price_per_1m_output`), `VLLMConfig` (`hf_model_id` **required**, `quantization`, `vllm_kwargs`, `sampling`), `IntrospectConfig` (`hf_model_id` and `log_dir` **both required**, `capture`, `device_map`, `torch_dtype`, `sampling`). Those fields are required rather than validated later so "a vLLM setup with no weights" and "capture with nowhere to write" are unrepresentable — which is also why each backend's `from_config()` only has to guard the one reachable case, *this entry has no such setup*. **One entry may populate more than one setup**: a model that is both a hosted endpoint and local weights is one model, so `venice-uncensored` carries `.api` and `.vllm`, and `ModelClient.create("venice-uncensored", backend_type="vllm")` binds the local one. There is deliberately **no separate `-vllm` row**. `backend_type` names which **setup** a row defaults to — `"api"`/`"vllm"`/`"introspect"`, each matching its field, so `getattr(cfg, cfg.backend_type)` is uniform. Which API *provider* an `.api` uses is that config's own `backend_type`, keeping endpoint identity out of the entry-level selector; which setup is bound decides the budget, since a backend built from the local setup carries `rpm=None` and no `extra_body`, so binding it never inherits the endpoint's limits or provider params. `model_compute_config(model, backend_type=None)` answers "what can this model's transport do?" straight off the backend *class*, without building anything — the lookup `jailbreak/chain.py` uses to decide whether a request is capturable, since constructing a local transport just to ask would load weights. `api_model_id` is the identifier sent **upstream** when the provider's slug differs from the registry name — Venice versioning `venice-uncensored` to `venice-uncensored-1-2` is the live case. The registry name stays the library's stable identity because it keys roles, rate-limit windows, telemetry rows and the price lookup (`telemetry.summary()` does `MODEL_REGISTRY.get(event['model'])`), so renaming an entry on a provider bump would orphan past traces *and* silently break costing; only the request payload uses the slug. Same role `hf_model_id` plays for the local setups. A logical `role` (`uncensored_gen`, `translation`, `constitution_gen`, `paraphraser`, `debug_local`) powers `default_model_for_role()` lookup. `register_model(name, backend_type=..., api=..., vllm=..., introspect=...)` only *composes* already-valid pieces; `ModelConfig` then checks what needs the whole picture (at least one setup is present; the default `backend_type` has its config; `recommended_max_workers` suits the provider, via `backends/capabilities.py`'s `validate_concurrency()`, which reads each backend's `compute_config` off the class so no transport is constructed). Validation raises rather than asserting, since `python -O` strips asserts and this guards caller-supplied input. `get_model_config()` raises `KeyError` for an unregistered model rather than silently returning a generic-default config. The `sampling` dicts hold per-model generation defaults that have no identity field of their own (`top_p`, `top_k`, ...), so they are bound at backend construction instead of being magic numbers inside `generate()`.

**`router.py`**: helpers over a `ModelClient`: `generate_sample()` (a batch of one, unwrapped), `batch_generate_samples()` (chunks of `batch_size`, with a per-chunk progress label and `internals_ids` sliced per chunk; a `batch_size` below 1 raises), and `assert_single_sample_per_call()` (the guard against several samples per call under internals capture). All of them delegate execution to the client; **nothing here decides how a batch runs**. The verdict rule and the check loops (`is_accepted`, `check_sample`, `batch_check_samples`, `checked`, `extracted`) are in `llm_pipeline/check.py`, since reading a verdict is orchestration, not transport.

`rate_limit_scope` says *whose* budget `rpm` describes: `"model"` (the default — Venice meters each model separately, so three models on one key hold three independent windows) or `"endpoint"` (Anthropic meters the *account*, so every model behind one provider+URL+key shares a single window). `ModelClient.create()` resolves it once, handing endpoint-scoped models both a shared `RateLimiter` **and** the endpoint id as their window key — either alone still yields independent windows, which is the whole bug. Models sharing an endpoint under that scope must declare the same `rpm`, checked at client construction so runtime `register_model()` is covered too. Deliberately governs rate limiting only: `recommended_max_workers` is pipeline depth, not a budget that adds up across models. **`wrappers.py`**: `RateLimiter` and `BatchCaller` both take a **finished backend** and read what they need straight off it (`backend.rpm`, `backend.max_workers`, `backend.compute_config`) — no registry lookups, no param resolution, and no import of `ModelClient` (which is what *holds* them; the old `BatchCaller._call_one()` calling back into `client.generate()` was a re-entrancy hazard). `RateLimiter` is a thread-safe sliding-window RPM enforcer keyed per model, and is inert when `backend.rpm is None` — i.e. for any local binding, even one whose registry entry also describes a rate-limited endpoint. `BatchCaller` has no notion of native batching at all; it reads exactly two capability flags — `supports_parallel_calls` (`_check_concurrency()`, run once in `__init__`, raises if `max_workers>1` on a series-only backend, whether that's Anthropic's tight limits or GPU contention) and `supports_internals` (`_check_internals_support()`). `from_model()` is gone: concurrency defaults to `backend.max_workers`, already clamped at backend construction, so the normal path can't be over-concurrent; an explicit `max_workers=` override still raises rather than silently degrading. Same treatment for `internals_ids` on a backend with `supports_internals=False`. `assert_single_sample_per_call(client, samples_per_call)` (in `router.py`) is the shared guard for pipelines shaped like `run_from_constitution` (one LLM call can return several samples) — raises when internals capture is requested against a multi-sample-per-call setting, since one forward pass's internals can't be attributed to any single resulting sample. Called by `run_from_constitution`.

**`prompting/`**: `load_prompt(pipeline, category, prompt_dir=None)` reads a prompt JSON, preferring a user override **per file** over the packaged copy. `PromptTemplate` renders it in two stages — `system_prompt`/few-shot fixed once at construction from build-time kwargs, `template` rendered fresh each call from call-time kwargs — so a checker validating many samples with the same system prompt builds one instance and calls it once per sample instead of re-rendering an identical system prompt every time (what `content_moderation/checker.py`'s four checker-builders used to hand-roll independently). `build_messages()` is the one-shot special case (construct and call together, same kwargs for both stages) that covers every other real caller. `format_style=` (one of `llms.prompting.EXTRACTION_STYLES`) appends the matching multi-sample output-format instruction (loaded from `prompts/format_instructions/{style}/`, not a hardcoded string) to `system_prompt` automatically.

**`llm_pipeline/`** sits between the stages and `llms/` and imports only `redact.llms` and `redact.exceptions`. `LLMRequest(model, messages, ...)` is a pending call a generator yields; it may carry its own `client`, `max_tokens` and `internals_id`. `drive_sync` drives one generator with a blocking call; `drive_generators` drives many round by round, one batch per client per round; `drive_units(source, on_done, on_error, pool_size, cap)` drives a pool of `(key, generator)` units topped up from a lazy source (the planned units of a stage), calling `on_done`/`on_error` per unit as it finishes. Each round it admits units into free slots and groups the pending requests by model, setup and reply limit; a group of `cap` requests (the stages pass `batch_size`) goes out as one `generate()`, and the largest group goes when none is full. **The async lane:** a request whose client has `supports_async_calls` (vLLM, OpenAI-compatible) is never grouped. It goes to the `llms/aio.py` loop the moment its unit yields it, at most `backend.max_workers` per model in flight, and its reply is handed back the moment it lands, so a slot never waits on a longer reply; while lane requests are in flight only full calls go out. `pool_size(batch_size, *clients)` is `max(2 * batch_size, widest lane among the clients)`, so a local engine is kept as full as it can run and `batch_size` only sizes calls to the backends without async calls (Anthropic, introspection). Requests still in flight when `drive_units` exits, on an error or Ctrl-C, are cancelled. A unit's own exception goes to `on_error`; a failed `generate()` or async request propagates and fails the run, except an async request's `PromptTooLongError`, which is raised inside its unit at the `yield` (so a stage fails that unit alone). `check.py` holds the verdict rule (`is_accepted`), `check_sample`/`batch_check_samples`, and the per-unit retry steps `checked()` (generate, check, regenerate with the verdict) and `extracted()` (generate until a reply parses).

### `telemetry.py`, `llms/resources/`, `residency/` — what a run cost, and what fits on the GPU

Both follow the same rule as the rest of the LLM layer: **instrument where the data exists, decide where the policy belongs.** `llms/` emits facts and stays dependency-free; the top level owns configuration, aggregation and export. No vendor SDK is ever imported from `llms/`.

**`llms/observe.py`** is the emit hook and nothing else — `record(event)`, `set_emitter(fn)`, `set_stage(label)`, defaulting to a no-op so a bare `import redact.llms` costs one dict lookup and pulls in nothing. It's a module function rather than a method on `LLMBackend` because `vllm._engine()` (a module function — the engine is cached per *checkpoint*, not per backend instance) has to emit too. `record()` never raises (the emitter's exception is logged at DEBUG): a broken sink must not take down a working generation run. **Granularity contract: a `call` event is one real transport call, with `n_items` the items it carried.** For vLLM the transport call is one engine request, so a batch of 32 is 32 events; the per-model `calls` in the summary count requests there.

**`telemetry.py`** owns the other half. `install(data_dir)` registers the emitter; `stage(label)` is a context manager labelling everything inside it (a plain module global, not a `ContextVar` — `ThreadPoolExecutor` doesn't propagate context to workers, so a ContextVar would read empty for every call `BatchCaller` fans out). `REDACT_TRACE=jsonl|wandb|off` picks the sink, read from the environment when `install()` runs. **JSONL is the default and always on**: `<data_dir>/Datasets/<run_id>.trace.jsonl`, the same vocabulary as the existing `.manifest.jsonl`/`.state.jsonl` sidecars, no account and no dependency, so the trace is already there when a run goes wrong. W&B is the only vendor adapter and only replays the same events, so the two can never disagree.

**Logger compatibility is a hard constraint, not a nicety.** The library attaches only a `NullHandler` and sets no level — configuring logging is the *application's* call (`scripts/run.py` does `basicConfig` with `--quiet`/`--debug`). So the JSONL sink is a plain file writer, **never a `logging.Handler`**: attaching one to the `redact` root would hijack the caller's configuration and make the trace depend on their log level. Human-readable summaries *do* go through `getLogger("redact.telemetry")` at INFO, so the existing flags already control them. Nothing in `telemetry.py` calls `basicConfig()` or `setLevel()`, and a test asserts exactly that.

**Two cost meters, because two different things are being bought.** API cost is tokens × price, per *model* (`price_per_1m_input`/`price_per_1m_output` on `APIConfig`). Local cost is engine **wall-clock lifetime** × GPU rate, per *checkpoint* — the GPU is leased whenever an engine is alive, so model load, CUDA-graph compile, KV preallocation and every gap for checker CPU work all count. That's why the lifetime timer lives with `_engine()` in `backends/vllm.py` (started on load, stopped in `clear_cache()`/`atexit`) and not on a backend instance: `venice-uncensored[vllm]` and `venice-paraphraser` share one load, so the cost centre is the engine cache key. Per-call duration is kept for *allocation* — distributing lifetime cost proportionally is what makes "is translation dominating this run?" answerable. Rates come from `configs/llm/gpu_pricing.json` (provider → GPU name → hourly USD), with the GPU detected via `nvidia-smi --query-gpu=name` (one line per device, so the name matches the table and the count is the device count); `REDACT_GPU_PROVIDER` selects the provider and defaults to `local` at rate 0. An unpriced GPU reports **time only** — a wrong rate is worse than no rate. Billing is on GPUs *rented*, since you rent the whole pod, with GPUs *used* reported alongside so idle capacity is visible.

**`residency/`** answers "does this fit?" before anything loads. `footprint(model)` resolves the **weights** as **declared → estimated → unknown**: the setup's `vram_gb` if set (weights only, total across its GPUs), otherwise `estimate.estimate()` from the checkpoint's HF config, otherwise unknown. The KV cache is always estimated on top (vLLM only), at the setup's `max_model_len` or else `estimate.DEFAULT_MAX_MODEL_LEN` (10,000 tokens, capped by the checkpoint's own maximum; the same value is passed to the engine at load), and the planning figure adds x1.1 + 0.6 GiB per GPU. `plan_residency(models, backend_types=None, *, gpus=None, gib_per_gpu=None, copies=None)` places the engines and returns a `ResidencyPlan` (`groups`, `gpus_required`, `fits`, `problems`, `warnings`, `explain()`, `as_dict()`); pass `gpus`/`gib_per_gpu` to plan for a machine other than the detected one. Models sharing a checkpoint are **one engine**. A single-GPU vLLM engine goes on the card with the most room, a tensor-parallel one (`min_gpus > 1`, matching its `tensor_parallel_size`) on untouched cards, numbered over those `CUDA_VISIBLE_DEVICES` leaves visible; idle cards take copies of the plan's first single-GPU vLLM engine (vLLM's `data_parallel_size`) unless the recipe gives `copies`. `gpu_memory_utilization` is an output: each engine is granted its padded need plus a share of its card's spare memory, and `apply_plan()` hands that grant and the cards to the load (`VLLMConfig` rejects one in `vllm_kwargs`); a grant below the padded need is a problem and the plan does not fit. **Per stage**: `plan_phases` makes one plan per stage (a `Phase`: its resident models and plan). An engine is resident from the first stage that calls it to the last; one kept for a later stage is unloaded for a stage it does not fit beside, and loaded again. The driver enters each phase in turn (see the top-level section): `unload_local(keep=...)` releases what the stage leaves out (through vLLM's shutdown hook where the installed version has one, else garbage collection), and everything is released when the run ends. The paraphrase stage also releases its paraphrasers' engines between them when they cannot be resident together. The GPU count and card size come from `nvidia-smi` (torch is asked for the size only when `nvidia-smi` cannot give it, since asking torch starts CUDA in this process); with neither, the plan warns that placement was not checked. The plans are stored in the `residency` trace event and in `summary["residency"]`. What is not done yet is the `TODO(driver script)` block in `residency/__init__.py`.

**The KV-cache trap, and why estimation won.** vLLM preallocates `gpu_memory_utilization × total_VRAM` for weights *and* KV cache, so a naive `mem_get_info()` delta comes back as that fraction **regardless of model size** — measure the 3B debug model at `0.86` and you'd record "this 3B needs 86% of the card". Torch's own allocator would separate the weights out, but vLLM V1 runs its engine core in a separate process, so the parent never sees them. Since the number that mattered was either unusable or unobtainable — and is computable from config shapes anyway — the measure-and-cache loop was deleted in favour of `llms/resources/estimate.py`. `measure.py` still records `claimed_gib`/`weights_gib` for the introspection backend's load event (it loads in-process), and its `free_total_gib()` is the planner's fallback for the card size; no measurement feeds back into planning.

**Preload.** `residency.preload()` warms local models on one background daemon thread (sequentially — concurrent loads compete for the same VRAM headroom) so a multi-minute 24B load overlaps with the constitution stage's Opus API calls instead of waiting behind it. The driver calls it as it enters each stage, for that stage's models and the next stage's when they fit beside them. **A failed preload logs at ERROR and records a `preload_failed` event, but never aborts the run**: an API-only stage is ledger-backed and its expensive output is saved as it goes, so finishing it beats killing it — the stage that actually needs the model fails on its own, at the point of use, with the cause already in the log. This is only safe because every transport cache uses **double-checked locking** (`vllm._engine`, `introspection._load`, both `_sdk_client`s): without it, a preload thread and the first real call missing together would each build an engine, putting two copies of a checkpoint on one card. A regression test spawns four threads and asserts the loader ran once.

### `multi_turn/` — General multi-turn conversation datasets

Use-case-agnostic. A **`Setting`** (`participants`, `max_turns`, optional `stop(transcript)`, `name`) played on a seed gives a **`Trajectory`** (`input_id`, `setting`, `transcript`, `turns_used`, `stop_reason`): the seed is the first participant's message, then the participants take turns in order until `max_turns` (the seed counts as one) or until `stop` is true. A **`Transcript`** is a typed step log: `message`/`reply` steps carry a chat role and are sent to models (`as_messages()`); `strategy`/`analysis`/`evaluation` steps are notes, only logged. An **`Actor`**'s turn is a generator `turn(transcript)` that yields `LLMRequest`s and returns its `Step`s: `ScriptedActor` (the given messages in order, the last repeated; no model), `ModelActor` (one call on the visible transcript), `StrategyActor` (sends what a `propose(transcript, turn_index)` generator builds, logging its note as a `strategy` step; it keeps no state between turns). `conversation_gen(setting, seed)` is the generator; `run_conversation(setting, seed, call)` drives one with a blocking call.

**The stages.** `generate_conversations(seeds, setting, data_dir, iterations=1, resume=True, batch_size=256, ...)` plays the setting (a factory, or a template deep-copied per conversation) on every seed (a `seed`/`sample`/`prompt`/`text` column) `iterations` times. A unit is `(input_id, iteration)`: planned whole in `conversations.manifest.jsonl`, driven through `drive_units` (pool sized by the `ModelActor`s' clients), saved to `conversations.csv` (`sample_id` = `content_id("{input_id}:{iteration}")`, `input_id`, `iteration`, `setting`, `turns_used`, `stop_reason`, `transcript` as JSON, `category`, `entry_type`, `source="conversation"`) and acked in the ledger keyed `(input_id, iteration)`; a unit that raises gets a row with `stop_reason="ERROR: ..."` and is acked. `iteration` numbers independent stochastic variants, not escalation rounds. `evaluate_conversations(data_dir=..., judge_model=..., judge_system=None, scope="last_reply" | "transcript")` is the separable judge pass: the criterion is the judge's system prompt (default `prompts/conversation/judge`), the goal is the seed. It writes `conversations_scored.csv` (`sample_id`, `success`, `judge_reasoning`, `judge_model`, `scope`), ledger keyed `sample_id`; a transcript too long for the judge is scored failed and acked, any other unit error stops the stage. Conversations are not a recipe stage: call the functions. Internals capture is not wired in yet.

**Applications**, each its own top-level folder building on `multi_turn/` (never inside it): `multiturn_attacks/` — `build_attack_setting(target_model, "crescendo" | "pair", ...)` returns a Setting factory, an attacker `StrategyActor` then the target `ModelActor`. Crescendo sends `DEFAULT_CRESCENDO_FOLLOWUPS` (`configs/jailbreak/multi_turn/crescendo_followups.json`), optionally through a pure jailbreak technique; PAIR has an attacker model write each message (`prompts/conversation/pair_attacker`). `generate_attacks` / `score_attacks` wrap the two stages, scoring with `SUCCESS_JUDGE_SYSTEM` (`prompts/conversation/success_judge`). The target must be safety-trained and has no default. `optimization/` — `optimize(seed, target_model, candidates, judge_model, judge_system, beam=2, depth=3)` extends every frontier node by each candidate move, has the target reply to all of them in one round, scores the replies with the judge, keeps the `beam` best, and returns `(best_node, tree)`; `multiturn_attacks.optimize_attack` feeds it jailbreak moves.

Dependency direction: `multi_turn/` imports `llm_pipeline/`, `llms/` and `dataset/` only. Oriented toward Inspect (seed≈Sample, messages≈ChatMessage, step log≈events, Setting≈solver, judge≈scorer).

### `dataset/` — Data Handling

Rows on disk. A stage's output is a CSV under `Datasets/`: one file for most stages, and one `{category}/samples.csv` per category for the input samples. Files:

- `identity.py` — `content_id(text)` is the identity of a row: the MD5 of its text, cut to 16 hex characters. `row_id(row, text_col)` gives the id a row already carries in `sample_id`, or the content id of its text when it carries none. `row_ids(frame, text_col)` does the same for every row of a frame.
- `rows.py` — the rows of one CSV. `append_rows(path, rows)` appends them in one write that is synced to disk, in the column order of the file's header, and returns the size of the file. It raises on a row with a column the header lacks, and `check_columns` raises the same without writing. `read_rows` reads the file whole, `iter_rows` and `count_rows` read it in chunks, and `keys_in` gives the unit keys of its rows.
- `sidecar.py` — the two JSONL files beside a stage's output, both built on `JsonlSidecar`: the path beside the artifact (`.sidecar(artifact)`), `.exists()` / `.reset()`, and a read that skips a line it cannot parse. `Ledger` is the `*.state.jsonl` file of finished units, one record per unit, keyed on one or more fields (`Ledger(path, key_fields, casters)`). `.record(records, saved=)` appends in one synced write, and `.read()` / `.completed()` give the finished units. `Manifest` is the `*.manifest.jsonl` file of planned units. `.write(rows)` replaces the file whole through a temporary file, and `.load()` or iteration reads it back.
- `resume.py` — what a run skips and what a resume puts back (see **Resume model** below). `resume_state(ledger, resume=, artifact=, manifest=)` returns the keys of the finished units, or clears the stage for a fresh run, and `release_lock` gives back the stage's lock.
- `save.py` — how a save is made. `commit` and `CommitBuffer` write the rows of finished units and then their acks.
- `drop.py` — `drop_units` takes some units out of a stage for a fresh run of part of it.
- `categories.py` — the per-category tree `{category}/samples.csv` of input samples. `append_samples` adds samples to a category's file and skips those whose id is already in it, and `sample_row` builds one input row in the tree's column order. `merge_all(dataset_dir)` merges the accepted rows of every category under a directory. `merge_inputs(data_dir)` gives the accepted inputs of a run: those of the seeded tree `Datasets/constitution_inputs/` when it holds a category file, otherwise those of the categories directly under `Datasets/`. The output, jailbreak and paraphrase stages read their inputs through it when they are given none, and so does `build_dataset` when it finds no merged inputs file. `take_per_group` caps a merged frame per `(category, entry_type)`.
- `taxonomy.py` — `load_taxonomy` and `load_seeds` read the taxonomy and seed JSON files under `configs/`. `iter_categories` yields the categories of a taxonomy, and `get_seed_prompts` formats the seeds of a category for a prompt.
- `loading.py` — `load_hf_dataset` loads a published dataset from the HuggingFace Hub with column and row filters, and `load_from_config` does so from a JSON config under `configs/`.

### `jailbreak/` — Jailbreak Generation

**152 single-turn techniques** in **4 layers → 22 families**, as `configs/jailbreak/combination_spec.json` names them. `pool.py` checks at import that the spec's `techniques` and the registries (`get_all_{obfuscation,hacking,manipulation,request}_functions()`: 72 + 25 + 8 + 47) name the same techniques, and raises otherwise; `technique.tag()` sets each function's spec tags when `redact.jailbreak` is imported: `families`, `layer` and `within_layer_order` (from its **first** family), `complexity` (0–3), `requires_llm`, `requires_benign`, `encode_weight`, `max_tokens`.

| Layer (apply order) | Families (count) — LLM? |
|---|---|
| 1. `hacking` (max 1 per combo) | `framing` (5, pure) · `cognitive` (5, LLM, scenario→construction) · `persona` (15 = invented + 14 named, LLM) |
| 2. `manipulation` (max 1) | `fsh` (4) · `dap` (4) — `random_*` pure, `selected_*` LLM; all `requires_benign` (cached in `Data_cache/benign/`) |
| 3. `obfuscation` (no layer cap; ordered by `within_layer_order`) | ① `sensitive_words` (16, LLM; the 10 `to_sensitive_words_encode_*` are *also* in `encode`) ② `tokenbreak` (3, LLM) ③ `translation` (20, LLM) ④ `typos` (4, LLM) ⑤ `casual_writing` (9, pure) ⑥ `suffixes` (4) ⑦ `encode` (12; `encode_weight` light/heavy) ⑧ `structural` (3) ⑨ `ascii_art` (1, random of 16 pyfiglet fonts) |
| 4. `requests` (max 1; all pure) | `answer_format` (9) · `answer_language` (20, generated from JSON) · `continuation` (4) · `indirect` (6) · `distractor_prefix` (2) · `distractor_suffix` (2) · `impersonation` (1) · `temporal` (1) · `asking` (2) |

**A technique** (`technique.py`) is a transform `(prompt, **kw) -> (text, info)` or, when it calls a model, a generator that yields `LLMRequest`s, is resumed with each reply and returns `(text, info)`. `info` is `""` or `key=value;...`; a rejection's starts with `DISCARDED`. A technique with a random choice draws it from its `rng` keyword. The pure techniques' template text lives in `configs/jailbreak/{hacking,obfuscation,requests}/*_templates.json` (`directives.load_templates`); the model-calling ones load `prompts/jailbreak/...` and take the `prompt_dir` overlay. A family drawn from a list (translation, answer_language) is generated and bound with `globals().update`. To add a technique: write it in its layer's module, return it from the module's getter, and give it a spec entry (`families`, `complexity`, `requires_llm`, ...); import fails until both agree.

**Compatibility rules** (`rules.compatible`), each binding both ways (a forbidden pair is refused whichever was picked first):
- One technique per family; a multi-family technique blocks every family it belongs to. The spec's per-family `max_picks` is **not read**.
- Layer caps from `layer_max_picks`: 1 hacking / 1 manipulation / 1 request — so e.g. framing⊥persona⊥cognitive, fsh⊥dap, distractor_prefix⊥distractor_suffix.
- `cross_incompatible_with`, read from either family's list: fsh/dap ⊥ continuation, indirect, framing, persona, cognitive; continuation ⊥ indirect; structural ⊥ ascii_art; ascii_art ⊥ framing, persona, cognitive, fsh, dap.
- `manipulation_blocked_obfuscation`: fsh/dap never sit with `translation`, `ascii_art` or heavy full-text `encode` (base64, unicode_escape, ascii_ordinal, morse, braille); `sensitive_words_encode_*` stays allowed (word-level encoding keeps the Q&A readable).
- Complexity filters only in budget mode (`remaining_complexity`).

**Sampling** (`sampling.py`). Every pick is **family-first** (`_pick_by_family`): a family, then a technique within it, so the 20 translation languages count as one choice. *Budget-driven* `sample_combination`: hacking, manipulation and requests each join at their layer rate (the spec's `layer_rates`, overridable per call), obfuscation picks up to `max_obfuscations` families, all within `max_complexity`; phase 5 (`allow_request_obfuscation`) may add a light `encode` or a `translation` **after** the request, obfuscating the finished request. *Count-driven* `sample_exact_combination` (`exact_techniques=N`) picks exactly N compatible techniques and ignores the complexity budget.

**The plan** (`plan.py`). `plan_run` writes the whole plan before anything generates: one manifest row per input and round, `{sample_id, iteration, combination, settings, category, entry_type, status}`, a round's settings merged over the base key by key. Each `(category, entry_type, iteration)` group is **dealt** in `sample_id` order by a `_Dealer`: a layer joins while its picks are below `floor(rate × position + offset)` (a seeded offset per group and layer, so a group gets `rate × size` picks rounded down or up), and a family is picked by lowest count over its `family_weights` weight. A layer two or more picks short of its target in a group (no technique of it fitted the units' other picks) is logged as a WARNING naming the coverage file. `assign_combination` seeds each draw by `(seed, sample_id, iteration)`, so the plan does not depend on input order or chunking, and draws again (up to 8 times, uniformly) while the combination equals one the input already got. `coverage()` writes `<out>.coverage.csv` beside the manifest: per layer, family and technique, the count per category, entry type and iteration, with a zero row for each pool technique never drawn. `combination_of(names, registry)` replays a row in its recorded order through the registry of **every** technique, so a plan made with another pool still replays; an unknown name raises.

**Application order** (`chain.py`). `in_layer_order` sorts by `(layer_order index, within_layer_order)`: hacking → manipulation → obfuscation ①…⑨ → requests, so request templates wrap obfuscated text and structural/ascii_art are the outermost obfuscations; phase 5's pick goes after the request. `run_chain(techniques, text, ...)` runs transforms inline and yields a generator's requests, capped at the technique's `max_tokens` and, with capture, tagged `{root}/{technique}/{n}` when the request's model can capture. Each technique gets the kwargs it takes (`gen_model`, `translate_model`, `benign_data`, `prompt_dir`) and, with `rng_seed`, its own `random.Random` seeded by `(seed, input id, iteration, technique)`, so a replayed plan gives the same text. A step that changed nothing is recorded as `noop=<name>`; the first rejection stops the chain. `combine_techniques(*fns)` and `apply_combination(fn, prompt, client=...)` run one prompt synchronously; manual chaining checks no rule.

**The stage** (`pipeline.run_augmentation`; front `generate_jailbreaks`). `resume_state` (lock, ledger `jailbreaks.state.jsonl` keyed `(input_id, iteration)`), then the plan (kept and reused on a resume, since it is sampled), benign data when a pending unit's combination has a `requires_benign` technique, read off the plan rather than the pool (`manipulation.get_or_generate_benign_data`, cached in `Data_cache/benign/`), then `drive_units` over the pending units: `units.pending_units` builds a unit's generator only as the driver takes it, `pool_size(batch_size, client)` units are live; a request to a model with async calls goes out alone on the lane, and the others are grouped per model into calls of up to `batch_size`. `CommitBuffer` saves every 32 units. A row is the input's columns plus `sample_id` (`content_id` of the jailbreak text), `input_id`, `jailbreak`, `technique`, `technique_info`, `complexity`, `num_techniques`, `is_noop`, `accepted`, `reasoning`, `iteration`, `combination_spec_version`. A unit whose chain raises gets an error row (the prompt unchanged, not accepted, its own `sample_id`, `content_id("{input_id}:{iteration}")`) and is acked. The natural kind runs with `accept_noop=False`: a variation whose text is its input's is rejected (`reasoning` says unchanged). Translation is the cost hot spot: translate → check → retry, up to 4 attempts, so 2–8 calls on the translation-role model per translation. Internals are captured under a provisional `{input_id}/jailbreak/attempt_{iteration}` and renamed to `{input_id}/jailbreak/{sample_id}` once the text is known.

**The augmentation section** (`augmentation.py`): `generate_jailbreaks(augmentation=...)`, or a recipe's `augmentations`, is `{"adversarial": {...}, "natural": {...}}`. `resolve(section, kind)` overlays a kind given on its default from `configs/jailbreak/augmentations.json` and checks it (every error names the kind and key); a kind left out is the default, `null` switches it off. The stage runs `run_augmentation` once per kind that is on, with `technique_pool(kind)` and `rounds_of(kind)`: the **adversarial** kind (attacks) to `jailbreaks.csv`, the **natural** kind (natural variations) to `variations.csv`, which goes beside `output_path` when one is given, else to `paths.variations_csv(data_dir)`, unless `variations_path` says otherwise; each file has its own manifest, ledger and coverage table.

- Keys of both kinds: `entry_types` (`null` all), `translation` (bool; see below), `layers` (`deny`), `families` and `techniques` (`allow`, `deny`; `allow` `null` is everything), `pure_only`, `family_weights` (a family's dealing weight within its layer), `iterations`. Adversarial only: `max_complexity`, `max_obfuscations`, `layer_rates` (`hacking`, `manipulation`, `requests`, `request_obfuscation`, over the spec's), `allow_request_obfuscation`, `rounds` (`null`; `"escalation"`, i.e. `default_escalation_schedule()`: exactly 1 technique, exactly 2, then two rising budget rounds; or a list of rounds, each merged over the kind's settings, which sets `iterations`). Natural only: `exact_techniques` (default 1).
- **Overlay**: a value replaces the default's whole value, lists included, except `layers`/`families`/`techniques`, whose `allow` and `deny` overlay one by one: the list given replaces the default's list of that name, and a `deny` given alone also takes its names out of the default's `allow`. The natural kind must keep an allow list. `natural_only_families` (top level of `augmentations.json`, `casual_writing` today) are added to the adversarial `families.deny` unless its `families.allow` names them.
- **Translation** has its own switch: `translation` alone decides the translation family, in `technique_pool` (`pool.TRANSLATION`). `false` keeps it out whatever the lists say (a `families.deny` naming it changes nothing); `true` puts it in, taking it out of the family deny and adding it to an allow list when the kind has one. An allow list naming `translation` or one of its techniques while the switch is `false` raises, saying to set `"translation": true`. The packaged default is `false` in both kinds (each translation is 2–8 calls on the translation-role model, hosted today); once a local translation model is registered, flipping it is one line of `augmentations.json`. `resolve_role` plans the translation model only when a kind's pool has a translation technique, so only with the switch on.
- Defaults: the adversarial kind denies no family (only `natural_only_families`, added at resolve); the natural kind allows a list of mild families and techniques (typos, casual_writing, structural, answer_language, answer_format, asking, indirect, temporal, continuation, plus `to_leetspeak_basic` and two suffixes) and denies three answer-format directives.
- `build_dataset` adds the **accepted** rows of the variations file as the `natural_variation` part (`include_variations`, `variations_path`).
- The twelve flat keywords (`include_*` ×5, `pure_only`, `max_complexity`, `max_obfuscations`, `sampling_probs`, `iterations`, `settings_per_iteration`, `entry_types`; `FLAT_KEYWORDS`) are deprecated aliases into the adversarial kind for one release, each with a `DeprecationWarning` (`apply_flat_keywords`: `include_<layer>` → `layers.deny`, `include_translation` → `translation`, `sampling_probs` → `layer_rates`, `settings_per_iteration` → `rounds`), wherever they are written: `generate_jailbreaks` keywords, the flat form of a recipe's `augmentations`, or `params["jailbreaks"]` (folded into the section by `augmentations_of`; a section-only key there raises).

**Known issues (not yet fixed):**
- Phase 5's request obfuscation is not counted against `max_obfuscations`.

**Reference list coverage:** Benchmarked against 73 instruction primitives + 74 request primitives. All feasible primitives are covered. Intentionally excluded: `agent_context_additional_instr` (system-prompt access required), `fine_tuning` (out of scope), `use_highly_specialized_language` (unclear path), `direct_question` (no-op). The library is a strict superset of the reference list on everything else, with additional techniques not in the reference set (ASCII art, adversarial suffixes, structural wrapping, cognitive hacking, manipulation, continuation attacks, indirect embedding, casual writing, extra encodings, extra languages).

### `content_moderation/` — Content Moderation Generation

Four stage cores, each called by its front in `stages.py`:

- **Seeded inputs** (`InputPipeline.run_from_constitution`, `inputs.py`; front `generate_inputs(constitution_df=...)`, the recommended path). Each constitution entry is one unit: a generation call for `samples_per_entry` samples, made again while the reply holds another count (up to `max_attempts`; a reply is rejected whole, never salvaged), then one check call per sample with the entry-type-aware `build_quality_checker`. A rejected sample is saved with its reason; an entry rejected on every attempt, or whose prompt is too long for the model, is acked `rejected` with no rows. The generation prompt lists the first 20 texts this run generated as do-not-repeat and counts the rest; a text is written once per folder. Rows go to `Datasets/constitution_inputs/{category}/samples.csv` (`SAMPLE_COLUMNS` plus `entry_type`, `subcategory`, `source_sample_description`, `constitution_category`, `source_group_tag`, `template_style`, `rejection_reason`); `style` (`long`, `short`, or any directory under `prompts/input/generation/from_constitution/`) picks the template. The ledger `constitution_inputs.state.jsonl` in the folder is keyed `(sample_description, entry_type, style)`; `resume=False` starts that style over and keeps the other styles' rows and acks (`drop_units`). It returns a `ConstitutionInputResult` (totals); the front reads the tree back and writes `constitution_inputs_merged.csv` for `build_dataset`. With internals capture, one sample per call is enforced (`assert_single_sample_per_call`).
- **Standalone inputs** (`run_standalone_inputs` → `InputPipeline.run_standalone`, `standalone.py`; front `generate_inputs` without a constitution). **Deprecated**: the front emits `DeprecationWarning`; it stays as the cheap quick-eval path. Per category: a description and seed prompts (`metaprompt.py`, each generated again until a reply parses; or hand-written seeds with `use_metaprompt=False`), then turns of generate, extract, drop texts already in the category, check, save every sample, with the turn's rejection reasons fed into the next turn, until `samples_per_category` are accepted, `3 × ceil(target / samples_per_request)` turns pass, or a turn extracts nothing. It has no discrete units, so no manifest and no ledger: it resumes by extending `Datasets/{category}/samples.csv`, and `resume=False` removes those files.
- **Outputs** (`run_output_generation`, `outputs.py`; front `generate_outputs`). One `llm_pipeline.checked` unit per input row with its own entry-type-aware `build_output_quality_checker`: a refusal of a harmful input is rejected, a benign input's reply is judged as any answer. `max_attempts > 1` regenerates a rejected response with the verdict as feedback. A prompt too long for the model gets a rejected row with an empty response. Writes `output_responses.csv` (`input_id`, `sample_id`, `input_prompt`, `category`, `subcategory`, `entry_type`, `output_response`, `accepted`, `rejection_reason`, `model`, `source`), ledger keyed `input_id`. The front caps inputs per `(category, entry_type)` with `max_per_category` (`take_per_group`), then globally with `max_samples`.
- **Paraphrase** (`run_paraphrase_target`, `paraphrase.py`; front `generate_paraphrases`). `k` paraphrases per base input and per accepted base output; each unit `(input_id, iteration)` gets a paraphraser from `paraphrase_pool(paraphraser)` (`"distribution"` is every `paraphraser`-role model) by a seeded hash. A separate checker (`build_paraphrase_checker`, by default on the `uncensored_gen` model; the front warns when it is also a paraphraser) drops a paraphrase that changes the meaning, and a duplicate is dropped; every attempted unit is acked, a dropped one too (`dropped_dedup`). Writes `paraphrases_inputs.csv` / `paraphrases_outputs.csv`. The paraphraser stands in for the defingerprinting model trained in another repository; when the pool's models cannot be resident together, the stage releases their engines between them.

`checker.py`'s builders return `(original, sample) -> messages`, the contract of `llm_pipeline.check`, each loading its prompt once as a `PromptTemplate`. `feedback.py` gathers the prompt text the stages add at run time (rejection feedback, the do-not-repeat note); it moves to prompt JSON later.

### `constitution/` — Constitution Generation

Generates structured category hierarchies for constitutional classifier training. Each constitution spans 4 severity levels:

1. **Absolutely harmful** — clear-cut violations, always flag
2. **Dual-use harmful** — borderline, harmful framing, debatable
3. **Dual-use benign** — borderline, benign framing, could look harmful
4. **Absolutely benign** — clearly safe, never flag (hard negatives)

`ConstitutionPipeline(client, output_dir=None).run(taxonomy, ...)` (front: `generate_constitution`, model role `constitution_gen`, Claude Opus by default) makes one call per **unit**: a `(source_category, entry_type)` pair for each of the first `num_taxonomy_categories` taxonomy categories and each entry type (all four by default), asking for `num_categories` constitution categories, plus, with `include_standalone_benign`, one `general::general_benign` unit with no taxonomy category. `units.py` plans the units (`plan_units`), builds each call from `prompts/constitution/{entry_type}/` (`messages_of`) and turns a reply into rows (`rows_of`, via `parse.parse_constitution`). A reply without its `[END]` marker (stopped at the token limit or by a provider filter) or with no entry that parses is rejected whole and the call made again, up to 3 attempts (`llm_pipeline.extracted`); a unit rejected every time is acked `rejected` with no rows, skipped on resume and named in a warning. The units run one at a time through `drive_units(pool_size=1)`; a failed call stops the run and the units saved before it stay acked.

Rows (`sample_id` = `content_id(sample_description)`, `constitution_category`, `constitution_subcategory`, `sample_description`, `entry_type`, `source_category`, `source_group_tag`, `model`) go to `{entry_type}.csv` and `merged.csv` under `Data_cache/constitution/`, saved per unit through `CommitBuffer(every=1)` before the unit's ack. The plan is `constitution.manifest.jsonl`, the ledger `constitution.state.jsonl`, keyed `source_category::entry_type`; it is a plain ledger (no lock, no recorded sizes), so a crash between a unit's two appends leaves it un-acked and the next run appends its rows again. `resume=False` removes the CSVs, the ledger and the plan first. `run()` returns `read_constitution(output_dir)`: `merged.csv` with every cell as text and an empty one as `""` (an empty frame with the columns when there is none), rows of earlier runs included; the driver reads the constitution the same way to seed a training run's inputs. Each entry later seeds `samples_per_entry` inputs (see `content_moderation/`).

## Prompt JSON Schema

All prompts are stored as `.json` files in `src/redact/prompts/{pipeline}/{category}/`, loaded at runtime via `load_prompt(pipeline, category)` in `llms/prompting/prompts.py`. `load_prompt` resolves to the single `.json` in that directory, else `template.json`.

**`prompt_dir` is an overlay, not a replacement.** Each prompt is read from the user's directory if present and from the packaged tree otherwise, so customizing one checker means copying one file, and the rest keep the library's later improvements. `report_prompt_sources(prompt_dir)` logs the resulting picture once at startup (what is overridden, and any directory matching no packaged prompt — a typo that overrides nothing is otherwise invisible). `scripts/scaffold_prompts.py TARGET` writes an editable starting tree: real prompts by default, `--empty` for TODO skeletons whose key set mirrors each real file's. Pipeline names in use: `input` (e.g. `input/generation/standalone`, `input/generation/from_constitution/{style}`, `input/quality_check`, `input/category_check`), `output` (`output/generation`, `output/quality_check`), `paraphrase` (`paraphrase/generation`, `paraphrase/check`), `jailbreak` (per-technique: `scenario_generation`, `jailbreak_construction`, `extract_harmful`, `benign_generation`, `category_selection`, `rewrite_with_typos`, `synonym_substitution`, `translate`, `translate_retry`, `translate_check`, ...), `constitution` (one per entry type, flat), and `format_instructions` (`numbered`/`structured_qa` — not a chat prompt, a `{"instruction": "..."}` snippet `PromptTemplate`'s `format_style=` appends to another prompt's `system_prompt`).

```json
{
  "system_prompt": "...",
  "template": "... {Category} ... {SeedPrompts} ...",
  "seed_fields": ["Category", "SeedPrompts"],
  "few_shot_examples": [],
  "metadata": {
    "version": "1.0",
    "notes": ""
  }
}
```

A prompt file carries no `category` or `pipeline` field: its directory is its identity, addressed as `load_prompt(pipeline, category)`.

`build_messages(config, **kwargs)` renders both `system_prompt` and `template` with the same kwargs (via `str.format_map`), so any placeholder works in either field. `seed_fields` is documentation only — render kwargs are whatever the caller passes.

## Usage

Every front takes one **`data_dir`** working root, a **role-defaulted model** per role (`None` is the registry role's default: constitution → `constitution_gen` (Claude Opus), generation and checking → `uncensored_gen`, translation → `translation`, paraphrase → `paraphraser`), `prompt_dir`, and **`resume`** (default `True`). A model name resolves through the registry (`llms/model_config.py`) to a `ModelClient`; for a custom endpoint, `register_model()` it.

```python
from redact import (
    generate_constitution, generate_inputs, generate_outputs,
    generate_jailbreaks, generate_paraphrases, build_dataset, run_pipeline,
)

DATA_DIR = "./runs/training"

# Training: inputs seeded from a constitution; they land in Datasets/constitution_inputs/.
constitution = generate_constitution(data_dir=DATA_DIR, num_taxonomy_categories=3)
inputs = generate_inputs(data_dir=DATA_DIR, constitution_df=constitution, samples_per_entry=3)

# Eval: standalone meta-prompt inputs (deprecated, emits DeprecationWarning; the cheap path).
inputs = generate_inputs(data_dir=DATA_DIR, samples_per_category=15, num_categories=3)

outputs = generate_outputs(data_dir=DATA_DIR, inputs=inputs)        # responses + output checker
jailbreaks = generate_jailbreaks(data_dir=DATA_DIR, inputs=inputs)  # attacks + natural variations, defaults
jailbreaks = generate_jailbreaks(data_dir=DATA_DIR, inputs=inputs, augmentation={
    "adversarial": {"entry_types": ["harmful"], "rounds": "escalation"},
    "natural": None,                                                  # no variations.csv
})
paraphrases = generate_paraphrases(data_dir=DATA_DIR, target="both")
dataset = build_dataset(data_dir=DATA_DIR, mode="training")         # paraphrases merged in

summary = run_pipeline("src/redact/configs/runs/training_example.json")   # or scripts/run.py
```

`build_dataset(mode="eval")` writes the paraphrases to `paraphrased.csv` instead of merging them. The `*_path` overrides (`output_path`, `variations_path`, `manifest_path`, `benign_path`, `inputs_path`, `outputs_path`, `jailbreak_path`, `responses_path`, ...) move one file; `taxonomy_dir`/`prompt_dir` relocate config and prompt inputs.

## Key Design Decisions

- **Prompts are external** — No prompts hardcoded in library code. Adding a new category = adding a JSON file.
- **Backends are swappable** — Switching from API to vLLM is a config change, not a code change.
- **Inputs are per-category** — input samples land in `{category}/samples.csv` (seeded ones under `Datasets/constitution_inputs/`); every other stage writes one CSV under `Datasets/`. Merging is explicit (`build_dataset`).
- **Checker reasoning feeds back to generator** — Rejection is not just a signal; the checker's reasoning is passed into the next generation call for directed improvement.
- **`Data_cache/` is internal** — Intermediate artifacts (benign samples, partial batches) go here, never in `Datasets/`.
- **Resume model — one modular sidecar system** — Every batched stage plans and resumes through the *same* two sidecar files, both built on `redact.dataset.JsonlSidecar`: a `<artifact>.manifest.jsonl` **plan** (`redact.dataset.Manifest`, one row per unit, written whole *before* generation) and a `<artifact>.state.jsonl` **ledger** (`redact.dataset.Ledger`, one record per *finished* unit). **A save is two synced appends** (`commit` / `CommitBuffer` in `dataset/save.py`): the rows of the finished units go to the output with `append_rows`, then their acks go to the ledger, and the last ack carries `_saved`, the size and a checksum of every file of the stage after that save. A unit is acked only once its rows are on disk, and a save counts only once its `_saved` line is. A new ledger opens with an empty `_saved` line, written before the first rows. **A resumed run reads the ledger alone.** `resume_state(ledger, resume=True, artifact=...)` takes the stage's lock, checks each output file against the size and checksum the ledger recorded, cuts off what a save that did not finish left behind, and returns the keys of the finished units. The bytes it cuts off are kept in `<file>.cut`, the ledger is cut back to its last `_saved` line, and the units of the unfinished save run again, so no unit ends with two sets of rows. It reads no row of the output. A file that is missing, shorter than recorded, or different in the last 4 kB before the recorded size stops the resume with a `RuntimeError` that names the remedies. A folder written before the ledger recorded sizes is taken over once: its output is read for the unit keys of its rows, and one ledger write acks them and records the sizes. **The lock** is `<ledger name>.lock` beside the ledger (`filelock`). It makes one process the writer of a stage from `resume_state` until the stage's `CommitBuffer` exits, or until `release_lock` for a run that finds nothing to save, and a second run on the same output is refused. Each save also checks that every file still has the size the ledger last recorded. `resume=False` starts over: the output, its `.cut` files and the ledger are removed, and the plan is written anew. A stage of several output files names their folder and the pattern they match (the seeded inputs: `artifact=folder, pattern="*/samples.csv"`), and a fresh run of one style of the seeded inputs removes that style's rows and acks alone (`drop_units`). The constitution stage names no output to `resume_state`, so its ledger is a plain one, with no lock, no sizes and nothing cut; it clears and reads its own CSVs. One rule about the model calls keeps an interrupted run honest as well: a failed batch **dispatch** propagates (it is the transport failing, not the units, so it must never be turned into acked rows — only a generator's own exception is isolated). Both files key on the *same* per-stage unit id: constitution `source_category::entry_type`; CM-input-from-constitution `(sample_description, entry_type, style)`; CM-output `input_id`; paraphrase / jailbreaks / natural variations / conversations `(input_id, iteration)`; conversation-scoring `sample_id` (ledger only — it scores existing rows). The jailbreak stage keeps its manifest on a resumed run and streams its units from it, since its plan is sampled; the other stages write their manifest again from their inputs. **Only exception:** standalone meta-prompt input generation has no discrete idempotent units (open-ended toward a sample-count target) — no manifest, no ledger; it resumes by extending its CSVs and is now **deprecated** (emits `DeprecationWarning`) in favour of constitution-seeded generation, though still functional. When adding a stage, use `Manifest`, `Ledger`, `resume_state` and `CommitBuffer`, don't hand-roll `*.jsonl` read/write.
- **Concurrency is capability-driven, and settled at construction** — a backend binds `max_workers` from its setup's `recommended_max_workers`, clamped there against its class's own `supports_parallel_calls`; `ModelClient` then picks the dispatch mode of `generate()` once from `supports_native_batching` (the whole list to the vLLM engine / parallel API thread-pool / series-only sequential), and `drive_units` sends a request on the async lane exactly when its backend has `supports_async_calls`. Nothing re-decides either per call. Overriding concurrency on a backend that can't support it still raises rather than silently degrading.
- **Every dataset row has a `sample_id`** (its own content-hash identity) **and, where it has a traceable origin, an `input_id`** (the origin row's `sample_id`) — the same pairing pattern everywhere: CM input's `sample_id` is the root of the chain (no `input_id` — it *is* the origin); CM output, jailbreak, and paraphrase rows carry both (jailbreak's `sample_id` = `content_id(jailbreak_text)`, computed in `jailbreak/units.py: row_of()`, never inherited from the input row, so every technique/iteration variant has its own; an error row's is `content_id("{input_id}:{iteration}")`); conversations carry both too. Constitution generation's entries also get a `sample_id` (hash of `sample_description`) despite having no downstream consumer yet. When adding a stage, give every row a `sample_id`; add `input_id` only when there's a real origin row to point at.
- **Internals capture is a non-interfering hook, never a CSV column** — it must never touch a pipeline's CSVs, schema, control flow, ledger, or manifest; it only writes to `{log_dir}/...`. `internals_id(s)` is never a generic kwarg threaded through every layer's signature; it's an explicit param only `TransformersIntrospectionBackend`, `BatchCaller`, and `LLMRequest` (read by the drivers) know about, and the path is rooted at the stage's own `input_id` so no new id scheme exists anywhere. `ModelClient.generate()` and `BatchCaller` both check `compute_config.supports_internals` and raise `ValueError` before dispatch if unsupported — never a silent crash three layers down inside a third-party SDK call. Wired across `generate_outputs`, `run_from_constitution`, paraphrase, and jailbreak (see the `introspection_backend.py` bullet above for the per-stage shapes); not yet multi-turn conversations. Full design/status: `.claude/introspection_backend_plan.md`.
- **Telemetry is emitted low and decided high** — `llms/observe.py` is a bare hook (`record`/`set_emitter`, no-op by default) so `llms/` imports nothing upward and carries no optional dependency; `telemetry.py` at the top level owns sinks, config, aggregation and cost. A `call` event is **one transport call**, with `n_items` the items it carried; for vLLM that is one engine request per item. The JSONL trace is always on and is a plain file writer, never a `logging.Handler`: the library sets no log level and attaches no handler, and telemetry must not change that.
- **Cost is metered at the granularity the thing is actually bought** — tokens per *model* for APIs, engine wall-clock lifetime per *checkpoint* for local (the GPU is leased while an engine is alive, and two models sharing a load share one meter). Per-call duration exists to *allocate* that lifetime cost, not to measure it. Same principle as the caches: endpoint→SDK client, checkpoint→engine, model→rate-limit window.
- **A footprint is computed, not measured** — planning runs on `llms/resources/estimate.py`, which derives weights and KV from the checkpoint's HF config (shapes only, no load, no cache to go stale) and adds *explicit* headroom. Measuring was tried and removed: vLLM preallocates `gpu_memory_utilization × card` so the card delta describes the setting rather than the model, and the one honest number (torch's allocator high-water) is invisible because the V1 engine core runs in a separate process. `vram_gb` in the registry is now the **override** for the weights when you know them better — an MoE checkpoint, or a measured figure — not the fallback. `resources/measure.py` holds the `nvidia-smi` probes (`detect_gpus`, `detect_gpu_memory_gib`) that the planner and the cost roll-up share, and otherwise survives as a post-hoc diagnostic feeding telemetry's `claimed_gib`. Everything is GiB.
- **src/ layout** — Prevents accidental imports of local code during testing. Package is properly installable via `pip install -e .`.

## Runner Scripts

A run is a recipe (plus its params file) handed to `run_pipeline`, or to `scripts/run.py RECIPE`, which configures logging and prints the summary; `src/redact/configs/runs/` holds an eval and a training example. Each stage logs its acceptance counts and leaves a `{stage}.run.json` record; `scripts/inspect_run.py DATA_DIR` prints them.

Rejection rate is the primary quality signal. A sustained high rejection rate indicates either a bad prompt (improvable) or a model capability ceiling (not improvable).

---

## Generation Strategy

Diversity comes from the seeds: each constitution entry (a category, subcategory, severity and sample description) drives its own generation call, and `style` picks the template (`long`, `short`). Within a run the seeded stage lists the first texts it generated as do-not-repeat, and a text is written once per folder. The standalone path uses per-category metaprompt seeds, a do-not-repeat list of the category's existing samples, and the previous turn's rejection reasons as feedback.

Four reference projects informed this architecture. All located in `../reference_files/` relative to this repo. Listed in order of influence:

Contains `constitution_gen.ipynb` (generation notebook) and `constitution.csv` (output). This pipeline will be integrated into REDACT as a new generation module.

## Public Release Notes

Prompts and template files ship with the library (`prompts/`, `configs/`); there is no redaction step. To change a prompt, overlay it: `scripts/scaffold_prompts.py TARGET_DIR` writes an editable copy of `prompts/` (`--empty` for TODO skeletons), and `prompt_dir=TARGET_DIR` reads each prompt from there when present. Before publishing a release, clear `Datasets/` and `Data_cache/`.
