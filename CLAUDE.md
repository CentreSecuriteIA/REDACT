# REDACT — Red-team Dataset Automation & Construction Toolkit

> Developer documentation: [docs/](docs/README.md), one page per stage and per layer, published at <https://centresecuriteia.github.io/REDACT/>.

## Project Overview

A modular pipeline for automated red-teaming dataset generation, built from the BELLS-O dataset iterations (content moderation input/output, jailbreaks) and reusable for other synthetic data tasks.

A run takes a taxonomy and a recipe and gives one checked dataset: a constitution (sample descriptions per category at four severities, the two clear ends in an eval run, plus a general-benign part per benign-taxonomy category), input samples seeded from it and checked by a second model, model responses, paraphrases, jailbreak attacks and natural variations, merged into one CSV (a training run) or three flat eval files (an eval run). Every stage saves as it goes and resumes where it stopped. The library is model-agnostic (hosted APIs or local vLLM engines, planned onto the GPUs), prompt-agnostic (prompts are JSON files, overlaid per file) and category-agnostic (a new category is a taxonomy entry). The product goal: a taxonomy and a task in, a dataset out, with defaults rather than settings.

Prompts and template files ship with the library. A `prompt_dir` overlays them file by file (`scripts/scaffold_prompts.py` writes an editable copy), and a recipe's `config_dir` overlays the dataset type, taxonomy, augmentation, generation axes and dimensions files the same way (`scripts/scaffold_setup.py` writes a folder of recipes and those files).

## Module Details

### Top level — `stages.py`, `recipe.py`, `driver.py`

A stage's public function (its **front**) may be called alone, from a notebook or a test; everything about a *run* (serving, residency, telemetry, run records, counting) lives in the driver, which reads what it needs about each stage from one table.

**Fronts** (`stages.py`): `generate_constitution`, `generate_inputs`, `generate_outputs`, `generate_paraphrases`, `generate_jailbreaks`, `build_dataset`. Each stage front but `build_dataset` takes `data_dir` (the working root; every path derives from it through `paths.py`), a model name per role (`None` is the registry role's default), `prompt_dir`, `resume` (default `True`), `verbose`, `read_back` (`False` returns an empty frame) and its tunables; `build_dataset` takes `data_dir`, `mode` (the dataset type), its part paths and `include_*` flags, `exclude_from` (eval only), `verbose` and `read_back`, and returns the complete dataset's rows, or in eval mode `{"inputs", "outputs", "jailbreaks"}` frames. A front resolves its inputs (the frame given, else `dataset.merge_inputs(data_dir)`), its clients (`ModelClient.create`) and its output path (`paths.*(data_dir)` unless an `*_path` override is given), then calls its core: `ConstitutionPipeline.run`, `InputPipeline.run_from_constitution`, `run_output_generation`, `run_paraphrase_target` (per target), `jailbreak.pipeline.run_augmentation` (per augmentation kind), `dataset.write_concat`. The core owns the manifest, the ledger, `resume_state` and `CommitBuffer`; the front never touches a ledger.
- When the inputs hold no accepted row (all rejected, or an empty frame given), the outputs, jailbreak and paraphrase fronts log a WARNING (`<stage> skipped: ...`), write nothing and return an empty frame, so a recipe run goes on; with `resume=False` they first remove what an earlier run left (`dataset.clear_stage`: the output, its `.cut` and `.tmp` files, ledger, manifest, the outputs stage's plan file and coverage table, and a jailbreak kind's coverage table, plan file, variants table and scenarios table). A jailbreak kind whose `entry_types` match no input, or whose section leaves its pool empty (`technique_pool(kind)` is `[]`, as with every layer denied), is skipped and cleared the same way, where an empty pool once planned an accepted identity no-op per input. With no input tree at all, `generate_outputs` and `generate_jailbreaks` raise `ValueError`; `generate_paraphrases` skips the target at INFO.
- `generate_inputs` and `generate_outputs` take `axes` (`None` the table's, `False` none, or `{axis: {value: weight}}`), `axes_weighting` (`"table"`, the default, or `"log"`), `seed` (42) and `config_dir`, and resolve the axes (`content_moderation.axes.resolve`) before anything runs. `generate_outputs` also takes `modes` (the answer modes each entry type allows, over the default; `content_moderation.modes.resolve_modes`, before anything runs) and `outputs_per_input` (responses per input, default 1; a whole number of at least 1, `check_outputs_per_input`).
- `generate_inputs` takes the constitution frame (`None`: the constitution saved under `data_dir`, else `ValueError`), then copies the accepted rows of every category file into `constitution_inputs_merged.csv` for `build_dataset`, removes that file when no row is accepted, and warns when under half of the generated samples are accepted. `generate_paraphrases` returns a frame per target that ran (`{"inputs": df}` by default; `target` `"inputs"`, `"outputs"` or `"both"`).

**The `Stage` table**: `STAGES` maps each recipe stage name, in the order of a full run (`constitution`, `inputs`, `outputs`, `paraphrase`, `jailbreaks`, `build`; a run takes its recipe's order, unchecked), to a frozen `Stage(name, front, roles, files, recipe_kwargs, sources, folded=(), extra_counts=None)`: the front's name, looked up on `redact` when the stage runs (`Stage.run`); the `(recipe role, registry role)` pairs it calls; `files(ctx)`, the CSVs that hold its rows and the column values a counted row holds; `recipe_kwargs(ctx)`, what the run passes the front (a value an earlier stage saves is a `Saved`, read when its stage starts: the constitution that seeds the inputs); `sources(ctx)`, the files it reads its inputs from (those that exist go in its run record; `[]` for none); `folded`, the params keys the run folds into a kwarg it passes itself (the jailbreak stage's flat keywords, into its `augmentation`); `extra_counts(ctx)`, what the stage counts beyond its files' rows, read after it ran (the build's `excluded`; the paraphrase stage's `skipped`). `Stage.params(ctx)` is the dataset type file's params for the stage with the params file's laid over them key by key. `Stage.check(ctx)` raises for a params key the front does not take or one the run passes itself, reading no stage file; `run_pipeline` calls it for every listed stage before the first runs, and `Stage.kwargs(ctx)` lays the checked params over the recipe kwargs. `RunContext`: `data_dir`, `dataset_type`, `models` (recipe role → name), `prompt_dir`, `taxonomy`, `taxonomy_dir`, `params`, `augmentations` (both kinds resolved), `resume`, `verbose`, `benign_taxonomy`, `config_dir`. A new stage is a core, a front and a row (`docs/extending.md`).

**Driver** (`driver.py`): `run_pipeline(recipe, params=None, verbose=True, data_dir=None)`:
1. builds the `RunContext`, checks every stage's params, then `check_dimensions` over every stage's axes, whichever stages run; installs telemetry; with `verbose`, logs the prompt overlay (`report_prompt_sources`); warns about the `config_dir` files no run reads, with `verbose` logs those it reads, logs the packaged natural families its copy of `augmentations.json` does not allow and, in an eval run, warns naming the techniques its copies add to the eval pool, and warns naming the families a differing copy of the run's dataset type file draws none of (`report_config_sources`);
2. notes the engines loaded already (`residency.loaded_engines()`), sets the run's serving (`capabilities.set_run_serving`) and plans residency per stage (`residency.plan_phases`; a plan that does not fit is logged, never fatal; a planning error is logged at ERROR with its traceback, saying every local engine then loads unplanned at 0.9 of a card);
3. before any model loads, `_check_cards` reads `nvidia-smi` once (`measure.card_use`) and raises `RuntimeError` when another process holds memory on a planned card, naming the cards, the processes and, found with `psutil`, the vLLM engine processes above them (titled `VLLM::`) in one `kill -9` line; a process on an unplanned card, or 1 GiB or more in use on a planned card with no process listed, only warns;
4. per stage: enters the stage's phase (unloads the engines the stage's plan leaves out, keeping those loaded before the run that no stage calls; an engine loaded before the run for a later stage is unloaded too, when this stage's plan, with the next one's when its models load ahead, leaves it out and has an engine still to load (`_strays`), and loads again for its stage; preloads the stage's local models and the next stage's when they fit beside them), runs `stage.run(read_back=False, **stage.kwargs(ctx))` inside `telemetry.stage(name)`, counts rows from `stage.files(ctx)` (`file_counts`; no stage reads its rows back) plus `stage.extra_counts(ctx)`, and writes the run record `{data_dir}/Datasets/{stage}.run.json` (`write_record`: `stage`, `timestamp` (UTC, with its offset), `params` (the merged ones), `models`, `counts`, `sources`, `serving` (per role: `name`, `backend_type`, and `copies` as planned, or `workers`), `dataset_type`, `dataset_type_hash` (`recipe.dataset_type_hash`: the content id of the type file as parsed), with a `config_dir` that folder and `config_files`; the `jailbreaks` record adds `spec_version`, `rules` (the `rules` id of each kind's plan file, by kind, `stages.jailbreak_rules`; `null` for a kind without one) and `augmentation`; the `build` record adds `spec_version`, the spec its rows' `families` and `layers` were read off);
5. `finally`: clears the serving; with a plan, waits for the preload threads at most `vllm.EXIT_WAIT_S` (60 s) together; unloads the engines the run loaded with a 10 s wait (which ends a load still running; engines loaded before the run stay), also without a plan after a planning error (which clears the loader's planned shares and cards itself); with a plan, clears the planned shares and cards; rolls telemetry up, after a failed stage too, without masking the stage's error, then uninstalls it (`telemetry.uninstall()`), so a front called after the run, as from a notebook, records into neither its trace nor its roll-up.

It returns `{dataset_type, data_dir, stages: {name: {counts, manifest}}, serving, telemetry}`, plus `residency` and `trace` when present (`data_dir` the root the run wrote under, `get_output_dir()` when the recipe names none; `"manifest"` is the record's path, a key kept by that name). A record's `models` leaves the `models` object's comment keys out. The jailbreak stage's section takes the flat keywords of its params as `stage_params` gives them, the type file's included. The driver logs `[<stage>] <counts> -> record <stage>.run.json` per stage. `scripts/run.py RECIPE [--params P] [--data-dir D] [--quiet|--debug]` is the CLI: it configures logging (`--debug` sets the `redact` logger alone to DEBUG); the first Ctrl-C or SIGTERM exits through the `finally`, and a second calls `terminate_engine_processes(all=True, quiet=True)` (SIGTERM to the engine processes and their descendants, SIGKILL 5 s later, no other child; written to stderr without logging, with a `kill -9` line for any pid still alive) and exits with `os._exit`. `scripts/inspect_run.py DATA_DIR` prints one line per stage record (timestamp, counts, models). `redact.pipelines`, `redact.runconfig` and the names `manifest_path`/`write_manifest`/`read_manifest` are aliases kept for one release, each with a `DeprecationWarning`: the two modules warn when imported, the three names when read from `redact.driver` or (`read_manifest`/`write_manifest`, out of `__all__`) from `redact`, through a module `__getattr__` (`driver.former_record_name`).

**Package root**: `__init__.py` attaches a `NullHandler` to the `redact` logger and sets no level, loads `.env` from `get_output_dir()` (its values win over the shell's) before the subpackages import, and lists its re-exports in `__all__`. Importing seeds nothing; `set_seed(seed=42)` seeds `random` and `numpy` when the caller asks. `paths.get_output_dir()` is `REDACT_OUTPUT_DIR`, else the first folder above the package holding `pyproject.toml` or `.git`, else the current directory. `exceptions.py` holds `RedactError` and `PromptTooLongError(RedactError)`, which a backend raises for a prompt over the model's context (see `llm_pipeline/`); elsewhere the library raises built-in errors.

### `llms/` — LLM abstraction layer

Everything above this layer calls one interface and reads capability flags; nothing branches on a backend's type. `llms/` imports nothing above it but the leaf modules `paths` and `exceptions`.

**Backends** (`backends/base.py`). A backend **is a configured model**: `from_config(config)` binds everything fixed about one model on one setup — name, `default_max_tokens`/`default_temperature`, system-prompt policy, `rpm`, `max_workers`, provider parameters, sampling defaults. Calls take only what varies: `generate(messages_list, *, max_tokens=None, temperature=None, internals_ids=None, **kwargs) -> list[str]` is batch-shaped (one sample is a batch of one), and backends with `supports_async_calls` add the coroutine `agenerate(messages, *, max_tokens=None, temperature=None, internals_id=None, **kwargs) -> str`. `_prepare()` applies `apply_system_prompt_policy` to each item: it splits system-role messages out (an empty one is dropped, so an empty system prompt counts as none) or, for a model with `supports_system_prompt=False`, folds them into the first user message (the first message when none is the user's), joined by a blank line, dropping empty ones; `_resolve()` fills `max_tokens`/`temperature` from the model's defaults. `max_workers` is clamped to 1 in `__init__` when the class has no `supports_parallel_calls`. Capabilities are one `compute_config` ClassVar, a frozen `ComputeConfig(supports_native_batching, supports_parallel_calls, supports_internals, supports_async_calls)`, read off the class without building a transport (which for a local one loads weights).

| Backend (`backends/`) | native batching | parallel calls | internals | async calls |
|---|---|---|---|---|
| `OpenAIBackend` (`openai.py`) | no | yes | no | yes |
| `AnthropicBackend` (`anthropic.py`) | no | no | no | no |
| `VLLMBackend` (`vllm.py`) | yes | yes | no | yes |
| `TransformersIntrospectionBackend` (`introspection.py`) | no | no | yes | no |

- `openai.py` — any OpenAI-compatible endpoint (the shipped entries use Venice and OpenRouter); the class has no provider logic, the endpoint lives in the entry's `APIConfig`. `ModelClient` fans a batch out through `BatchCaller`, one call per item; `agenerate()` runs on a cached async SDK client, so these models use the async lane. It sends `default_extra_body` with a call that passes no `extra_body`, maps a context-length error to `PromptTooLongError`, and warns on an empty reply and on a content-filter stop.
- `anthropic.py` — Claude through the native SDK: the system prompt goes as `system`, one call at a time; a temperature goes in `extra_body` (`messages.create()` has no `temperature` keyword from SDK 1.0), and none at all, with one warning, when the SDK sends API version 2026-10-21 (SDK 2.0+), which refuses it on every model; the reply is its text blocks joined (a thinking block has none); a 400 saying the prompt is too long (or that it and `max_tokens` exceed the context) raises `PromptTooLongError`; it warns on an empty reply.
- Both API backends: the SDK retries a failed call (a 429, a 5xx, a lost connection) `APIConfig.max_retries` times (default 2) with its own backoff, unseen by the rate limiter and the trace, and gives up after `APIConfig.timeout_s` (default `None`: the SDK's 10 minutes). A call that still fails stops the stage.
- `vllm.py` — vLLM's `AsyncLLM`, in this process (vLLM 0.31 or later, `MIN_VLLM`: the import error names an installed vLLM that is too old, and an older one that imports is warned about). Every item is its own engine request, awaited on the shared loop of `llms/aio.py`, and the engine batches whatever is in flight: `agenerate()` makes one request, `generate()` one per item and waits for all (one failure cancels the rest). `max_workers` is the engine's `max_num_seqs` times its copies: what the async lane keeps in flight. The engine loads with the residency plan's `gpu_memory_utilization` and cards (`set_planned_utilization`/`set_planned_devices`, kept out of the cache key), else 0.9 of the card; planned cards beyond one copy's span become `data_parallel_size` copies inside one engine, and each engine records the share and cards it was built with (`engine_grants()`). Without `max_model_len` the engine gets `estimate.effective_max_model_len()`: 10,000 tokens, capped at the checkpoint's longest context from its HF config, else from the first context field its `config.json` sets (read from the checkpoint folder or the hub cache, never downloaded); 10,000 when neither names one. A setup with `hf_config` is also given `tokenizer=<folder>`, unless its `vllm_kwargs` names a `tokenizer`: vLLM (0.31) reads the `config.json` of the folder it loads the tokenizer from as well as `hf_config_path`, so `tokenizer_folder.py` gathers the checkpoint's tokenizer and processor files (`TOKENIZER_FILES`, fetched alone with `snapshot_download` at the setup's `tokenizer_revision` or `revision`, served by the hub cache offline; a local `hf_model_id` is read in place), symlinked or, where the OS allows none, copied, beside a copy of the packaged `config.json`, in `$HF_HOME/assets/redact/tokenizers/<checkpoint>-<hash>` (the hash of the snapshot's path and the config's bytes: a new snapshot or a changed config gets a new folder, and one built before is reused). It is built at engine load under a lock, through a temporary folder renamed into place, and stays out of the cache key: it follows from the checkpoint and the config the key names, and the planner computes the key without fetching anything. Prompts go through the engine tokenizer's chat template, or the entry's `chat_template`; for a checkpoint without one (Mistral-3.x) pass `tokenizer_mode="mistral"` in `vllm_kwargs`. A prompt that fills the context or is longer raises `PromptTooLongError` for its request alone (`_is_prompt_too_long`: a validation error on `input_tokens`, or one whose message says the prompt is too long, as vLLM 0.31's is for a prompt of exactly `max_model_len` tokens, which names no parameter; any other validation error propagates); a request aborted by a release raises. Every request records one telemetry `call` event, a failed or cancelled one too (with `error`). Defaults: `temperature` 0.7, `top_p` 0.85, unless the entry sets them. Before an engine loads, `VLLM_WORKER_MULTIPROC_METHOD` defaults to `spawn` and, on WSL2, `VLLM_USE_V2_MODEL_RUNNER` to `0` (vLLM's V2 runner fails every load there); a value in the environment wins. With `"disable_log_stats": false` in `vllm_kwargs`, a task on the shared loop calls the engine's `do_log_stats()` every 10 s (vLLM prints its stats, prefix-cache hit rate included, only when asked; a failed call logs at DEBUG), stopped when the engine is released and at exit. A leading `|>` artifact (ChatML tokens missing from the vocabulary) is stripped.
- `introspection.py` — raw `transformers` inference that saves a model's internals (vLLM's continuous batching discards activations). `IntrospectConfig(hf_model_id, log_dir, capture={logprobs, hidden_states: False|"last"|"all", attention})`, default logprobs plus the last hidden state; capturing attention loads with `attn_implementation="eager"` unless `extra_kwargs` names one. Capture is opt-in per call: `internals_id(s)` is an id the caller computes, and the files go to `{log_dir}/{internals_id}/`, with an always-written `meta.json` (model, settings, input messages, output text); a capture replaces the files an earlier one left under the same id. `rename_capture(old_id, new_id)` (a no-op on the other backends) moves a capture made under a provisional id once the row's `sample_id` is known. A too-long prompt fails with whatever `transformers` raises.

**Caches.** A backend is cheap; what it uses is cached on that resource's own identity, behind double-checked locking: OpenAI SDK clients per `(base_url, api_key, max_retries, timeout_s)`, sync and async apart; the Anthropic client per `(api_key, max_retries, timeout_s)`; vLLM engines per `(hf_model_id, quantization, engine kwargs)`, so `venice-uncensored-fp8` and `venice-paraphraser` share one load (the bf16 `venice-uncensored` served with vLLM is another); transformers models per `(hf_model_id, device_map, torch_dtype, load kwargs)`, apart from vLLM's. A local backend holds only its engine's key and reads the engine on each call, so it never keeps a released engine alive. `clear_transport_caches()` clears all of them: an SDK client is closed (a backend built before fails on its next call), a local engine is shut down and its memory freed (a client built on it raises).

**`backends/capabilities.py`**: `BACKEND_TYPES` (transport name → class), `API_BACKEND_TYPES`, `SETUP_TYPES`; `resolve_setup(config, requested)` picks a setup — the one requested, the run's choice (`set_run_serving`, from the recipe), the entry's `backend_type`, the only setup present; `transport_for` maps it to a `BACKEND_TYPES` key (`api` becomes the `APIConfig`'s own `backend_type`); `backend_for(config, setup)` calls the class's `from_config`, with the run's `workers` in place of `recommended_max_workers` for an API setup; `validate_concurrency`, `compute_config_for`.

**`client.py`**: `ModelClient` is a configured backend plus its dispatch, chosen once in `__init__` from `compute_config`: a native-batching backend gets the whole list (the limiter charged once per batch); any other fans out through a `BatchCaller`. `ModelClient.create(model, backend_type=None)` resolves the setup, builds the backend and resolves its rate limit. There is no client cache: everything expensive is cached on its own identity, so a fresh client is microseconds, `clear_transport_caches()` frees memory, `clear_client_cache()` drops the shared rate-limit windows and endpoint rpm claims (tests, or after changing the registry), and a new API key takes effect. `generate(messages_list, ...)` is batch in, batch out; `agenerate(messages, ...)` makes one async call, charging the limiter per call (`RateLimiter.reserve()`), and raises without `supports_async_calls`; both raise `ValueError` when capture ids reach a backend without `supports_internals`. `rename_capture` delegates to the backend. The client resolves no params, builds no messages or checkers and reads no verdicts.

**Rate limits and fan-out** (`wrappers.py`). `RateLimiter` is a thread-safe 60-second sliding window; `shared_limiter(key)` gives one window per key: the model name, or under `rate_limit_scope="endpoint"` (Anthropic meters the account) the endpoint id, so every model on one provider, URL and key variable shares a window. Models sharing an endpoint window must declare the same `rpm`, checked in `ModelClient.create()`. `reserve()` asks without blocking, `wait_if_needed()` blocks; a backend with `rpm=None` (any local binding) is never limited. `BatchCaller` runs one call per item over `backend.max_workers` threads; it raises at construction for `max_workers` above 1 on a series-only backend, and in `run()` for `internals_ids` on a backend without `supports_internals`. Both take a finished backend and import no `ModelClient`.

**`model_config.py`**: `MODEL_REGISTRY`, loaded from `configs/llm/models.json` at import (every invalid entry is reported in one `ValueError`; `notes` is ignored). A `ModelConfig` is an identity — `name`, `roles` (a list; each must be in `configs/llm/roles.json`), `is_uncensored`, `supports_system_prompt`, `default_max_tokens`, `default_temperature`, `supports_temperature` (false for a model that rejects sampling settings, Claude Opus 4.7 and later, `claude-opus-5-5`: a call's temperature, the checks' 0.15 included, is not sent, and it may set no `default_temperature`) — plus one or more setups: `APIConfig` (`backend_type` `openai`|`anthropic`, `api_key_env`, `rpm`; `base_url`, required for `openai`; `api_model_id`, `rate_limit_scope`, `recommended_max_workers`, `default_extra_body`, `price_per_1m_input`/`price_per_1m_output`, `max_retries`, `timeout_s`), `VLLMConfig` (`hf_model_id`; `quantization`, `vllm_kwargs`, `sampling`, `vram_gb`, `min_gpus`, `hf_config`: a folder under `configs/llm/hf_configs/` whose `config.json` vLLM, as `hf_config_path`, and the estimator read in place of the checkpoint's own, and which the engine's tokenizer folder holds too (built at load, see `vllm.py`); it holds the checkpoint's `generation_config.json` as well, which vLLM also reads from there (without it TranslateGemma never stops at its end-of-turn token and runs every reply to `max_tokens`); `vllm_kwargs` may not name `hf_config_path`; `chat_template`, a Jinja string passed to `apply_chat_template` in place of the tokenizer's own, for a checkpoint that ships none: not an engine argument, so two entries on one checkpoint may differ in it and share the engine; `vllm_kwargs` may not name it), `IntrospectConfig` (`hf_model_id`, `log_dir`; `capture`, `device_map`, `torch_dtype`, `sampling`, `vram_gb`, `extra_kwargs`). Every config validates itself in `__post_init__` and raises (never asserts); the required fields make a setup without weights or without a log folder unrepresentable. One entry may carry several setups: `venice-uncensored` has `.api` and `.vllm`, and `ModelClient.create("venice-uncensored", backend_type="vllm")` binds the local one, which has no `rpm` and no `extra_body`. `backend_type` names the default setup (`api`, `vllm`, `introspect`, each matching its field; `None` means the only one present). The registry name is the stable identity (roles, rate-limit windows, telemetry rows, prices); `api_model_id` is what the provider receives when its id differs (`venice-uncensored` is sent as `venice-uncensored-1-2`), as `hf_model_id` is for the local setups. `default_model_for_role(role)` is the first entry in `models.json` order that lists the role; `get_models_by_role`, `available_roles`, `get_model_config` (`KeyError` for an unregistered name), and `model_compute_config(model, backend_type=None)`, the capability flags of a model's transport read off the class. `register_model(name, backend_type=None, roles=None, is_uncensored=False, supports_system_prompt=True, default_max_tokens=2000, default_temperature=None, api=None, vllm=None, introspect=None, supports_temperature=True)` adds or replaces an entry for the running process. The roles: `uncensored_gen`, `translation`, `machine_translation` (a model that only translates, in its own format; the translation technique checks its output and has the generation model judge it), `constitution_gen`, `paraphraser`, `debug_local`. Local entries: `venice-uncensored`'s `.vllm` (bf16), `venice-uncensored-fp8` (the same weights, FP8 on load, 24.9 GiB; shares its engine with `venice-paraphraser`), `translategemma-27b` (the default of the `translation` and `machine_translation` roles: vLLM, FP8 on load, `hf_config`, 4096 tokens, 28.4 GiB), `llama-3.2-3b-debug`, `humanizer-12b` (the `paraphraser` default, self-hosted: vLLM, bf16, 8192 tokens, 22.8 GiB, `chat_template`, revision and tokenizer revision pinned; listed before `venice-paraphraser`, which holds no role and is called by name); `deepseek-v3.2` is a hosted chat translator, called by name.

**`router.py`**: `generate_sample()` (a batch of one, unwrapped), `batch_generate_samples()` (chunks of `batch_size`, a progress label per chunk, `internals_ids` sliced per chunk; a `batch_size` below 1 raises), and `assert_single_sample_per_call(client, n)`, which raises when the backend can capture internals and `n` is not 1 (one forward pass's internals cannot be split between samples; no stage calls it now, since every call of the inputs stage asks for one sample).

**`prompting/`**: `load_prompt(pipeline, category, prompt_dir=None)` and `resolve_prompt` read a prompt JSON, the user's overlay file first, else the packaged one. `PromptTemplate` renders the system prompt and few-shot once (build-time kwargs) and the `template` per call; `PromptTemplate.load(pipeline, category, *, prompt_dir=None, few_shot=True, format_style=None, **build_kwargs)`. `build_messages(prompt_config, few_shot=True, format_style=None, **kwargs)` renders both at once. `format_style` (`numbered`, `structured_qa`) appends the format instruction from `prompts/format_instructions/{style}/` (`get_format_instruction`). `report_prompt_sources(prompt_dir)` logs the overrides and warns about override folders that match nothing (a `paraphrase/generation/<x>/` of a registered model is a `per-model override`, of any other name unused); one of a prompt that became one per answer mode (`output/generation`, `output/quality_check`; `_MOVED_PROMPTS`) is warned about as a `moved override`, naming its new place. `extraction.py`: `extract_numbered_list(text, strict=False)`, `extract_structured_qa`, `extract_and_clean` (with `expected_count`, a reply with another count is rejected whole), `clean_sample`. `scaffold.py`: `scaffold_prompt_tree(target_dir, source_dir=None, mode="copy", *, overwrite=False)` (a file to write that exists raises `FileExistsError`, naming the count and the first five, before any file is written), and `scaffold_setup(target_dir, *, overwrite=False)` (a setup folder for a recipe's `config_dir`; exported from `redact`).

**Also here**: `aio.py` (one event loop on a daemon thread for every async call: `submit`, `run`), `progress.py` (`ProgressReporter`, throttled progress lines), `observe.py` (the telemetry hook, below).

### `llm_pipeline/` — units of model calls, and how they are driven

Between the stages and `llms/`; imports only `redact.llms` and `redact.exceptions`, and reads or writes no file. `LLMRequest(model, messages, internals_id=None, *, client=None, max_tokens=None, temperature=None)` is a pending call a generator yields; `LLMRequest.for_client(client, messages, *, internals_id=None, max_tokens=None, temperature=None)` binds it to a client. Requests share a call only when their reply limits and temperatures agree.

- `drive_sync(gen, call)` drives one generator with a blocking call (`apply_combination`, `run_conversation`); `drive_generators(gens, *, finalize, ...)` drives many round by round, one call per client (or model), reply limit and temperature per round (`optimization/search.py`).
- `drive_units(source, *, on_done, on_error=None, pool_size, cap=None, resolve=None, progress=None)` drives a pool of `(key, generator)` units topped up from a lazy source, at most `pool_size` live, reporting each to `on_done` as it finishes. Each round it groups the pending requests by model, setup, reply limit and temperature; a group of `cap` requests goes out as one `generate()`, and the largest group goes when none is full and no async request is in flight.
- **The async lane**: a request whose client has `supports_async_calls` (OpenAI-compatible, vLLM) is never grouped. It goes to the `aio` loop the moment its unit yields it, at most `backend.max_workers` per model in flight, and its reply returns the moment it lands. `pool_size(batch_size, *clients)` is `max(2 * batch_size, widest lane among the clients)`, so a local engine is kept full and `batch_size` only sizes the grouped calls. Requests in flight when `drive_units` exits (an error, Ctrl-C) are cancelled.
- **Errors**: a unit's own exception goes to `on_error` (or propagates without one). A failed `generate()` or async request propagates and stops the stage, with one exception: an async request's `PromptTooLongError` is raised inside its unit at the `yield`. So on the lane the inputs stage acks that entry rejected, outputs writes a rejected row, jailbreaks and conversations an error row, paraphrase acks the unit `prompt_too_long`, scoring scores it false; on the grouped path (Anthropic, introspection) the error comes out of `generate()` and stops the stage. The constitution and benign units take no `on_error`, so a too-long prompt stops them on any backend.
- `check.py`: `is_accepted(reply)` (the first word, after whitespace, markdown and quotes, is yes/ok/okay/accept/accepted/pass/passed, any case; the checker prompts ask for a reply that starts with `Yes` or `No`, and the input, output and paraphrase ones say that the first word is the verdict and nothing comes before it), `check_sample`, `batch_check_samples`, and the unit steps `checked(gen, build_gen_messages, check=None, build_check_messages=None, *, original="", internals_ids=(None, None), max_tokens=(None, None), max_attempts=1, precheck=None, temperatures=(None, None))` (generate, check, regenerate with the verdict; `gen` and `check` each a client or a model name, as a jailbreak technique's requests carry it (the typo check); `temperatures` go to the (generation, check) requests; `precheck(text) -> reason`, a code-side verdict before the check: a reason rejects with no check request, and is the feedback) and `extracted(gen, build_gen_messages, extract, *, internals_id=None, max_tokens=None, max_attempts=3)` (generate until a reply parses; `gen` a client, or a model name as a jailbreak technique's requests carry it).

Every stage on the pool passes `pool_size=pool_size(batch_size, *its clients)` and `cap=batch_size`; the constitution runs one unit at a time (`pool_size=1`).

### `telemetry.py`, `llms/resources/`, `residency/` — what a run cost, and what fits on the GPU

Instrument where the data exists, decide where the policy belongs: `llms/` emits facts and imports no telemetry vendor SDK; the top level owns configuration, aggregation and export.

**`llms/observe.py`** is the hook: `record(event)`, `set_emitter(fn)`, `set_stage(label)`, `current_stage()`, and `first_in_stage(key)` (whether a key is new since the label was last set: the cut-reply warning's once per stage run). With no emitter `record()` returns at once; it never raises (an emitter's exception is logged at DEBUG). It is a module function because `vllm._engine()`, cached per checkpoint rather than per backend, emits too. A `call` event is one transport call, with `n_items` the items it carried: a hosted model makes one call per item and vLLM one engine request per item, so both give one event per item.

**`telemetry.py`**: `install(data_dir=None, sink=None)` registers a `Collector`; `REDACT_TRACE=jsonl|wandb|off` picks the sink (an unknown value warns and uses `jsonl`; `off` installs no collector, so the trace, the roll-up (`summary()` is `{}`) and the stage-end counts of cut replies are lost, while the backend's first-cut warning per stage and model still shows; `wandb` needs the `wandb` package, which no extra brings). The JSONL trace is `<data_dir>/Datasets/run-<YYYYMMDD-HHMMSS>.trace.jsonl` (UTC), or `-2`, `-3`, ... after the run id when that name is taken; it is written for `jsonl` and `wandb` alike, and W&B only replays the same events. `stage(label)` labels everything inside it (a module global, not a `ContextVar`, since thread pools do not pass context to workers), records the stage's duration, and on leaving logs per model the replies cut at the token limit (a `call` event's `cut: true`; the first per stage and model warns at once; `summary()["cut"]`). A `Collector` keeps the totals only, never the events (the trace holds them; a large run makes millions). `summary()` rolls up `models` (calls, items, tokens, `ms`, `cost_usd`), `local_s`, `local_billed_s`, `gpu`, `api_cost_usd`, `local_cost_usd`, `errors`, `cut`. **Logging**: the library attaches only a `NullHandler` and sets no level; the JSONL sink is a plain file writer, never a `logging.Handler`; the roll-up goes to `redact.telemetry` at INFO; nothing calls `basicConfig()` or `setLevel()` (a test asserts it).

**Cost** is metered as it is bought. Hosted: tokens × `price_per_1m_input`/`price_per_1m_output`, per model; a model served locally is never priced by tokens. Local: engine wall-clock lifetime, per checkpoint (the timer lives with `_engine()` in `backends/vllm.py`, from load to `clear_cache()`/exit, so two models sharing a load share one meter), load, compile and idle time included; billed time is the union of engine spans (`local_billed_s`) × the hourly rate × the GPUs on the machine (rented, not used). The rate: `set_gpu_rate()`, else `REDACT_GPU_HOURLY_USD`, else `configs/llm/gpu_pricing.json` under `REDACT_GPU_PROVIDER` (default `local`, at 0) by the GPU name `nvidia-smi` reports. An unpriced GPU reports time only.

**`llms/resources/`**: `estimate.py` sizes a local model from its HF config's shapes, read at the revision its setup pins (`vllm_kwargs["revision"]`; a packaged `hf_config` is read as it is), without loading it (weights, with quantization and MoE; KV cache at `max_model_len`, else `DEFAULT_MAX_MODEL_LEN` = 10,000 capped at the checkpoint's context, summed layer by layer, each at the full context, when the attention shape varies by layer (`per_layer_config`, or `layer_types` with `num_global_key_value_heads`/`global_head_dim`; Gemma 4's `config.json` names only `global_head_dim`, so read that way its full-attention layers count every KV head, which errs high); every field read through `_field`, so an attribute that raises (transformers 5.17's per-layer attributes) reads as unset; padded need `(weights + KV) × 1.1 + 0.6` GiB per card). Sizing is computed, not measured: vLLM preallocates `gpu_memory_utilization × card`, so a card's memory delta restates the setting, and the V1 engine core runs in another process, hiding torch's allocator. `vram_gb` in the registry overrides the weights when known better (an MoE checkpoint, a measured figure). `measure.py` holds the `nvidia-smi` probes — `gpu_cards()` (index, UUID, used and total memory, name, in one query), `card_use()` (plus compute processes), `detect_gpus()`, `card_sizes_gib()`, `visible_gpu_ids()` — and `visible_only`, `cuda_lock`, `bus_order`, `free_total_gib()` (torch, the fallback size), and `Measurement` (`claimed_gib`/`weights_gib` for the introspection load event). Everything is GiB.

**`residency/`** answers "does this fit?" before anything loads (`footprint.py`, `placement.py`, `plan.py`, `phases.py`, `lifecycle.py`, `explain.py`).
- **Footprint** (`footprint(model)`): weights declared (`vram_gb`) → estimated → unknown; KV for vLLM only. Models sharing a backend cache key are one engine, counted once.
- **Cards**: each card is planned at its own size from one `nvidia-smi` query (torch only when that fails, since it starts CUDA here; with neither the plan warns). Only the cards `CUDA_VISIBLE_DEVICES` leaves count, named by index, UUID or UUID prefix; as CUDA does, an entry that names no card ends the list. Planning and loading set `CUDA_DEVICE_ORDER=PCI_BUS_ID` unless it is set (engine processes start after it; a plan warns only when CUDA started in this process first and it places a transformers model off the CPU on two or more visible cards, or on one `CUDA_VISIBLE_DEVICES` names by index on a machine of several), and a build gets its cards by UUID, narrowing `CUDA_VISIBLE_DEVICES` for the process while it builds (`measure.visible_only` under `measure.cuda_lock`).
- **Placement** (`plan_residency(models, backend_types=None, *, gpus=None, gib_per_gpu=None, copies=None, pinned=None)` → `ResidencyPlan`): an engine already loaded (`pinned`, which only a caller passes; a run does not yet) first, on its own cards; a single-GPU vLLM engine on the emptiest card with room (lowest index on a tie), else the card with the most room; a tensor-parallel one (`min_gpus > 1`, equal to its `tensor_parallel_size`) on whole untouched cards; a transformers model where its `device_map` puts it. A model that does not fit starts a new group; with more than one group, `_Search` tries every card for up to 8 single-card engines (at most 20,000 tries) for one group with the fewest shared cards.
- **Copies** (vLLM `data_parallel_size`, inside one engine): when everything is one group, the first vLLM engine gets a copy on every other card with room, beside other models only where every engine keeps its need and never on a card smaller than its home card; the recipe's `copies` replaces that (`1` turns copies off). Tensor-parallel copies are planned, not yet loaded end to end on a GPU.
- **Grants**: on each card the vLLM engines split 0.9 of it, less what transformers models hold, each granted its padded need plus an equal share of the spare; an engine loads with the smallest grant any of its cards gives. `apply_plan()` hands grants and cards to the loader; `VLLMConfig` refuses a `gpu_memory_utilization` in `vllm_kwargs`. A grant below the padded need makes the engine `oversized` (listed once, by its first model), a problem.
- **`ResidencyPlan`**: `groups`, `gpus_required`, `gpus_available`, `gpu_name`, `per_gpu_gb` (the smallest card), `gib_per_card`, `oversized`, `machine_given`, `loaded`; `co_resident`, `sequential`, `fits`, `problems`, `warnings`, `footprints`, `explain()`, `as_dict()`. **An engine loaded already**: for the detected machine, a planned vLLM engine that is loaded is recorded in `loaded` with the share and cards it was built with (`lifecycle.loaded_grants`, from `vllm.engine_grants()`) and named in a WARNING, also in `warnings`: the plan's share and cards for it apply only after it is released. A loaded engine not in the plan is warned about too.
- **Per stage** (`plan_phases`): one `Phase` per stage (resident models, plan, loadable first group). An engine is resident from the first stage that calls it to the last, keeps the cards it loaded on, and loads with the smallest share any of its stages plans; one kept for a later stage is unloaded for a stage it crowds and loaded again, when every stage then fits. `unload_local(keep=, engines=, wait=)` releases what a stage leaves out (vLLM's shutdown hook, garbage collection, `torch.cuda.empty_cache()`). At the run's end every engine the run loaded is released, after a planning error too; those loaded before it (a notebook's) are kept. The paraphrase stage plans its own pool of paraphrasers and releases each before the next when they cannot be resident together. Plans go to the `residency` trace event and `summary["residency"]`; a plan that does not fit is logged at ERROR and never aborts the run.
- **Preload** (`preload(models, ..., wanted=None)`): one daemon thread loads the stage's local models, one after another, so a long load overlaps the API calls of an earlier stage; a model no longer `wanted` is skipped. A failed preload logs at ERROR and records `preload_failed`, never aborting the run: the stage that needs the model fails at the point of use. Double-checked locking in every transport cache (`vllm._engine`, `introspection._load`, both `_sdk_client`s) keeps a preload and a first call from building two engines; a regression test spawns four threads and asserts one load.

**Engine processes and the exit** (`backends/vllm.py`): each build records the processes it starts (engine cores and, with copies, the DP coordinator); a release ends what the shutdown leaves, and a failed build's processes are ended at once. `terminate_engine_processes(processes=(), *, all=False, quiet=False)` lists their children with `psutil`, sends SIGTERM, then SIGKILL to those alive 5 s later, and returns the pids still alive; `all=True` ends every engine process this process started and their descendants, and no other child. When a build with the plan's copies fails, one copy on the engine's first cards is built instead, once, with a WARNING naming `"copies": 1` (not when `data_parallel_size` came in `vllm_kwargs`, which only a `VLLMBackend` built by hand can do since a registry entry may not name it, when exiting, or when the failed build's processes outlive SIGKILL); the `load` event carries `planned_copies` and `fallback`. The exit hook releases every engine, waiting at most `EXIT_WAIT_S` (60 s) for a load in progress, then ends that build's processes so the load fails with `EngineLoadEnded`; no load starts after the hook. A release mid-run waits for a load however long it takes.

**Not done** (the `TODO(driver script)` block in `residency/__init__.py`): the paraphraser pool is planned apart from the run's plan; each card is sized by its total and assumed empty (`_check_cards` stops a `run_pipeline` run on a planned card another process holds; a plan made outside it is not checked); the unload search tries every candidate unloaded at once, so with more than 8 engines it can miss a run one unload would fit; a load that hangs is ended only on the way out or by a second signal. An engine loaded before the run that a stage calls counts only from the first stage that calls it: the driver unloads it on entering an earlier stage whose plan leaves it out and loads a model (tested offline only), and where it stays loaded it keeps the share and cards it was built with (warned about, not yet planned around with `pinned`), so a model planned beside it may fail to load; release it before the run. Offline tests cover the hang and second-signal paths.

### `multi_turn/` — General multi-turn conversation datasets (planned extension, not finished)

**Status:** a first version of a planned extension, together with `multiturn_attacks/` and `optimization/`: not part of a recipe run, not validated like the recipe stages, interfaces may change. Use-case-agnostic; not a recipe stage (call the functions); full reference in `docs/stages/conversations.md`. A **`Setting`** (`participants`, `max_turns`, optional `stop(transcript)`, `name`) played on a seed gives a **`Trajectory`** (`input_id`, `setting`, `transcript`, `turns_used`, `stop_reason`): the seed is the first participant's message, then the participants take turns until `max_turns` (the seed counts as one) or `stop` is true. A **`Transcript`** is a typed step log: `message`/`reply` steps carry a chat role and are sent to models (`as_messages()`); `strategy`/`analysis`/`evaluation` steps are notes, only logged. An **`Actor`**'s turn is a generator `turn(transcript)` that yields `LLMRequest`s and returns its `Step`s: `ScriptedActor` (the given messages in order, the last repeated), `ModelActor` (one call on the visible transcript), `StrategyActor` (sends what a `propose(transcript, turn_index)` generator builds, logging its note as a `strategy` step). `conversation_gen(setting, seed)` is the generator; `run_conversation(setting, seed, call)` drives one with a blocking call.

**The stages.** `generate_conversations(seeds, setting, data_dir, iterations=1, resume=True, batch_size=256, ...)` plays the setting (a factory, or a template deep-copied per conversation) on every seed (a `seed`/`sample`/`prompt`/`text` column) `iterations` times. A unit is `(input_id, iteration)`: planned in `conversations.manifest.jsonl`, driven through `drive_units` (pool sized by the `ModelActor`s' clients), saved to `conversations.csv` (`sample_id` = `content_id("{input_id}:{iteration}")`, `input_id`, `iteration`, `setting`, `turns_used`, `stop_reason`, `transcript` as JSON, `category`, `entry_type`, `source="conversation"`) and acked in the ledger keyed `(input_id, iteration)`. A unit that raises gets a row with `stop_reason="ERROR: ..."`, an empty `setting`, `turns_used` 0 and transcript `[]`, and is acked; a too-long prompt is such an error on the async lane, and stops the stage on an Anthropic or introspection binding. `iteration` numbers independent variants, not escalation rounds. `evaluate_conversations(data_dir=..., judge_model=..., judge_system=None, scope="last_reply" | "transcript", batch_size=32, ...)` is the separable judge pass: the criterion is the judge's system prompt (default `prompts/conversation/judge`), the goal is the seed. It writes `conversations_scored.csv` (`sample_id`, `success`, `judge_reasoning`, `judge_model`, `scope`), ledger keyed `sample_id`, no manifest. The judge and its prompt are resolved before `resume_state`, so a fresh scoring run with a bad judge stops before it clears anything. With the judge on the async lane a transcript too long for it is scored false and acked; on an Anthropic or introspection binding the stage stops. A conversation's `sample_id` does not change with its transcript: after a fresh conversation run, score with `resume=False` too. Internals capture is not wired in.

**Applications**, each its own top-level folder building on `multi_turn/` (never inside it): `multiturn_attacks/` — `build_attack_setting(target_model, "crescendo" | "pair", ...)` returns a Setting factory, an attacker `StrategyActor` then the target `ModelActor`. Crescendo sends `DEFAULT_CRESCENDO_FOLLOWUPS` (`configs/jailbreak/multi_turn/crescendo_followups.json`), optionally through a pure jailbreak technique; PAIR has an attacker model write each message (`prompts/conversation/pair_attacker`). `generate_attacks` / `score_attacks` wrap the two stages, scoring with `SUCCESS_JUDGE_SYSTEM` (`prompts/conversation/success_judge`). The target must be safety-trained and has no default. `optimization/` — `optimize(seed, target_model, candidates, judge_model, judge_system, beam=2, depth=3)` extends every frontier node by each candidate move, has the target reply to all of them in one round, scores the replies, keeps the `beam` best, and returns `(best_node, tree)`; `multiturn_attacks.optimize_attack` feeds it jailbreak moves.

Dependency direction: `multi_turn/` imports `llm_pipeline/`, `llms/`, `dataset/`, `paths` and `exceptions` only. Oriented toward Inspect (seed≈Sample, messages≈ChatMessage, step log≈events, Setting≈solver, judge≈scorer).

**A technique** (`technique.py`) is a transform `(prompt, **kw) -> (text, info)` or, when it calls a model, a generator that yields `LLMRequest`s, is resumed with each reply and returns `(text, info)`. `info` is `""` or `key=value;...`; a rejection's starts with `DISCARDED`. A technique with a random choice draws it from its `rng` keyword.

A technique may carry an **applicability**, `applicable(text, entry_type) -> bool`, set with `@applicable_when(predicate)` (`technique.py`; `applies(fn, text, entry_type)` reads it, true for a technique without one): the plan draws it only for an input it is true for (below). The predicate calls the helper the technique itself calls, so it cannot drift from what the technique does, and sees the input, not what earlier steps of a combination wrote; the registry fixture records `has_applicable`, a bool, not the function. Twenty-two techniques have one: `to_abbreviations` and `to_stripped_accents` (`casual_writing`) apply only to a text they change (`_abbreviated(text) != text`, `_without_accents(text) != text`), so a fresh natural plan no longer draws them as no-ops (`_without_accents` leaves a mark with no letter before it, a text that starts with one, as it is); a predicate that raises stops the plan with a `RuntimeError` naming the technique and the input (`plan._applicable`), not the bare error; the three benign roles apply to benign and dual-use benign inputs only (`benign_role.is_benign_input`, on the entry type alone), so no harmful or dual-use harmful input gets one; the three guardrail-address techniques apply to every input but an absolutely benign one (`guardrail_address.is_targeted_input`, the mirror), so a note that a message is benign is never put on one already benign; the four transliterations apply to a text with a Latin letter (`transliteration._has_latin`); the ten code-switches to a text of at least two words (`code_switching.can_mix`): one word is in one language, so each also refuses such a prompt before any call (`DISCARDED; reason=too short to mix`), which a kept plan may still name.

The pure techniques' template text lives in `configs/jailbreak/{hacking,obfuscation,requests}/*_templates.json` (and the encodings' decode hints in `obfuscation/decode_hints.json`, a directive per technique) as **variant pools**, one per directive, read by `directives.read_pools` whatever the file's shape (`{directive: [{name, template}]}`; continuation's `{name, prefix, suffix}`, the prompt between them unformatted; structural's `to_json`, `to_xml` and `to_markdown`, lists like the rest (its `policy_ids` is a list its module reads, not a pool); a persona frame of `persona_templates.json` is a single template, a pool of one named after its entry, beside its `mechanics`, a frame also naming `{mechanic}` exactly once (`persona_templates._check_mechanic_slots`); `personas.json` and `cognitive_techniques.json` are definitions, read with `load_templates`). A technique names its pool with `@uses_pool(file, directive, slots, info_key, request_slot)` (its `variant_pool`, a `PoolRef`; `info_key` the key of its info that names the variant drawn; the answer languages share one, set by their factory; `request_slot=False` for a pool whose templates hold no `{prompt}`, pieces the technique sets into another template, or fills with its own slots: the persona templates' mechanics, and the payload split's reassembly, whose slots are `{parts}` and `{names}`; `optional=True` for a pool drawn only at a rate: an encoding's decode hints, whose info names a variant, `hint=<name>`, only when one was drawn), and `pool.py` checks every named pool at import beside the spec and the dimensions (`check_pools`: non-empty unique names of letters, digits, `_` and `-` (a name goes into a row's info as `key=<name>`), `{prompt}` exactly once in each template of a pool with a request slot and no slot its technique does not fill, no slot with a conversion or a format spec (`{prompt!r}`, `{prompt:>9}`), no unknown key, an optional `weight` a number of at least 0, at least one variant above 0; an error names the file, directive and variant). `draw_variant` draws a pool without weights with `rng.choice`, so a seed draws what it drew before (`tests/fixtures/template_draws.json` pins every template technique's texts, infos and rng state by SHA-256 digest, and those of the eval pool's other techniques but the eight translations, 118 of its 126, `PYTHONPATH=src python -m tests.jailbreak.test_template_draws`), and a weighted one with `rng.choices`; weight 0 turns a variant off, a pool of one makes no draw. No packaged variant has a weight, and an eval-pool technique's may not (`test_directives.py`).

A count draw (the eval type, the natural kind, escalation rounds 1 and 2) and a draw without a dealer deal them as encode's members, so the eval draws do not move (its digest holds, and a test compares them with the key left out). The slot is not a family: `family_weights` cannot name it (a kind's section raises as for any name the kind does not draw, and `plan_run` called directly raises too); weighting `encode` scales it. *Budget-driven* `sample_combination`: phase 0, the rewrite layer, first, when the round includes it (`include_rewrite`, default false; `rounds_of` writes it, true, only for a kind that allows the layer while a rewrite technique is registered) at its rate (the spec's 0), decided only when included, at a rate above 0 and with a rewrite technique in the pool, so otherwise it makes no rng draw and no dealer call and every draw is the one made before the layer existed (a test pins it for both cases); then hacking, manipulation and requests, in that order, each join at their layer rate (the spec's `layer_rates`, overridable per call), then the obfuscations fill what the `max_complexity` budget leaves (the unit's allowance in its place under the group budget, see **The plan**), up to `max_obfuscations` families; phase 5 (`allow_request_obfuscation`) may add a light `encode` (the light `to_sensitive_words_encode_*` included) or a `translation` **after** the request, obfuscating the finished request, for a unit that drew a request only: a unit without one is not asked (no dealer call, no `rng` draw), so the step never lands after the outermost wrapper. Phase 5 is decided (the dealer's `include` at the `request_obfuscation` rate over the group's units, as the layers, so the units holding a request, 0.7 of them by default, take it more often; else an `rng` draw) and drawn before phase 4, so it reserves one of the `max_obfuscations` slots and its complexity, and a combination never holds more than `max_obfuscations` obfuscations (with 0 slots there is no phase 5); the combined function names it in `request_obfuscation`. With it false the sampler never decides it (no dealer call, no candidates drawn; a test holds it), so the draws are those of a sampler without the step; a digest of the budget draws (`test_the_budget_draws_are_the_pinned_ones`, a change detector, re-pinned on purpose with each change that moves a draw) and one of the eval type's draws pin them. *Count-driven* `sample_exact_combination` (`exact_techniques=N`) picks exactly N compatible techniques and ignores `max_complexity`, `max_obfuscations`, `layer_rates`, `allow_request_obfuscation` and `include_rewrite`: a rewrite technique in the pool is dealt as any family's, so the pool, not a rate, keeps the layer out of a count round. The apply order is the layers' whatever the pick order, a rewrite first; the coverage table and the shortfall WARNING name the rewrite layer as any other.

**The plan** (`plan.py`). `plan_run` writes the whole plan before anything generates: `<stem>.plan.json` (`plan_inputs`: `seed`, `rounds`, sorted pool names, `family_weights`, `layer_rates`, `spec_version`, the spec's `version`, which dates the pool, and `rules`, `rules_id(pool, rounds=)`: the content id of what the plan's draws read off the spec, its layer order, caps and rates, the manipulation block list, the request obfuscation's families and what it keeps out (only when a round allows the step: a budget round with `allow_request_obfuscation`), the heavy encodings' `heavy_encoding_weight` (only when a round is a budget round and the pool holds a heavy full-text encoding, `sampling.is_heavy_encoding`), each pool family's layer, `within_layer_order` and `cross_incompatible_with`, and each pool technique's families, complexity, `cross_incompatible_with` and `encode_weight`, comments aside, which can change while the version does not; written through `dataset/planfile.py`), then one manifest row per input and round, `{sample_id, iteration, combination, settings, category, entry_type, status}`, a round's settings merged over the base key by key (a round's `layer_rates` replaces the kind's whole). Each unit draws from the techniques of the pool that apply to its input (`applies`, on the input's text and entry type), in pool order: the whole pool when every one applies, so a pool without an applicability draws as before; a unit no technique of a layer applies to takes no pick there, the dealer giving the layer to the group's next unit that can take it, and a unit no technique applies to gets the empty combination (the identity). A kept plan replays without asking any predicate. Each `(category, entry_type, iteration)` group is **dealt** in `sample_id` order by a `Dealer` (`dataset/dealing.py`, shared with the generation axes): a layer (and phase 5's `request_obfuscation`, when allowed) joins while its picks are below `floor(rate × position + jitter)` (a jitter in [0, 1) seeded per group, layer and position, so two layers of one rate fall on the units independently), a family is picked by lowest count over its `family_weights` weight, and a technique within it by lowest count among the members the unit may take (`assign_combination` has `_observe` count each kept draw's families, the request obfuscation's under `REQUEST_SCOPE` and a budget draw's heavy full-text encodings under `HEAVY_ENCODINGS`, techniques, layers, request obfuscation and complexity; each group has its own dealer, nothing is shared across groups). The complexity budget still favours a family's cheaper members where they cost differently (`encode`, `sensitive_words`), as intended: complexity 3 fits only a unit whose earlier picks leave 3 points, and fsh/dap refuse the heavy `encode` members, so even in their slot each heavy `encode` member is drawn 3 to 5 times per 3,000 default attack units at seed 42 (3 to 6 over seeds 42 to 46) against 27 to 29 for one of complexity 2 (26 to 29).

**The group budget** (opt-in, off in every packaged kind and dataset type): an adversarial kind's `budget` `"group"` (default `"unit"`) lets a unit spend, in place of `max_complexity`, an allowance of `min(max_complexity + bank, ceiling)`, the bank what the group's earlier units left unspent of `max_complexity` each (`Dealer.bank(max_complexity)`, from the `spent` that `_observe` counts) and the ceiling `max_unit_complexity` (default `max_complexity + UNIT_HEADROOM`, 3). `assign_combination` works it out once per unit (`_allowance`) and every pick of the unit, a resample's too, fits what is left of it, so a group's mean complexity per unit stays at or below `max_complexity` and no unit exceeds the ceiling; each round and each group has its own bank, and a count round or a draw without a dealer ignores it. `rounds_of` writes `budget` to the rounds only when `"group"` and `max_unit_complexity` only when given, so a kind that leaves them out or says `"unit"` has the rounds, the plan file and the draws it had before (the pinned digests hold), a kept plan made without them resumes unchanged, and a section that turns the option on or off over a kept plan raises on resume, naming `rounds`. Measured over 3,000 units of the default attacks (seed 42, three groups, `max_complexity` 6, ceiling 9; `python -m tests.jailbreak.simulate 3000 budget`; in brackets the range over seeds 42 to 46; spec 1.4, `heavy_encoding_weight` 0.25), unit / group budget: mean complexity per unit 5.60 (5.59 to 5.62) / 6.00, highest unit 6 / 9, units above 6 0 / 859 (819 to 867), obfuscations per unit 1.49 (1.49 to 1.51) / 1.66, draws of complexity 3 or more 1,267 (1,250 to 1,267) / 1,367 (1,356 to 1,367), `encode`'s top member 7.44 (7.32 to 8.04) / 2.47 (2.47 to 3.48) times an even share and `sensitive_words`' 3.45 (3.24 to 3.57) / 1.58 (1.45 to 1.58). It evens out the cheap members and draws more techniques of complexity 3 or more: all ten of `encode`'s members of complexity 3 are drawn, 3 to 5 (3 to 6) / 3 to 6 (3 to 6) times each, and each of `sensitive_words`' four 13 to 15 (10 to 16) / 10 to 44 (6 to 44) times; the extra allowance goes to the obfuscations (2.54 / 2.94 complexity per unit, the other layers' spend unchanged). Whether to turn it on is undecided, and no default changes.

A fresh plan with the same seed draws differently from one made at spec 1.0 (member dealing, the persona and cognitive vs impersonation rule, phase 5 counted where it is on and its families counted apart, the script rule, translation ⊥ encode and the heavy encodings' slot (the first eval release), the applicability filter, the seven retired techniques, and the techniques specs 1.2 and 1.3 added, which are dealt too); a kept plan replays unchanged. `tests/jailbreak/simulate.py` plans N synthetic inputs through `plan_run` and gives each technique's share and its share within its family, and what the units spent in complexity (`spend`; `python -m tests.jailbreak.simulate N budget` compares the unit and the group budget); the coverage table holds neither. A layer, or the request obfuscation step, two or more picks short of its target in a group is logged as a WARNING naming the coverage file. `assign_combination` seeds each draw by `(seed, sample_id, iteration)`, so the plan does not depend on input order or chunking, and redraws without the dealer while the combination equals one the input already got (up to 8 draws in all). `coverage()` writes `<stem>.coverage.csv`: per layer, family and technique, the count per category, entry type and iteration, with a zero row for each pool technique never drawn. With `verbose`, `log_model_calls(manifest, pool)` then logs one INFO line, the plan's cost: how many planned units call a model (draw a `requires_llm` technique) and the calls the spec's `calls` imply, low to high, the translation family's apart. `combination_of(names, registry)` replays a row in its recorded order through the registry of **every** technique; an unknown name raises `ValueError` naming `resume=False`. `default_escalation_schedule()`: exactly 1 technique, exactly 2, then budget rounds `max_complexity` 6 / 9, `max_obfuscations` 2 / 3, rates hacking 0.7 / 0.9, manipulation 0.3 / 0.1, requests 0.8 / 0.9, request_obfuscation 0.5 / 0.7, `allow_request_obfuscation`.

**Application order** (`chain.py`). `in_layer_order` sorts by `(layer_order index, within_layer_order)`: rewrite → hacking → obfuscation ①…⑬ → requests → manipulation, so request templates wrap obfuscated text, structural or a neutral container, then ascii_art, are the outermost obfuscations, and phase 5's pick goes right after the request (`sampling.py` inserts it there). The manipulation layer applies last since the first eval release: fsh, dap and fake_turns put the finished question, obfuscated and with its request, among their examples or after their invented turn, so the obfuscations, the request and the model steps (a typo rewrite, a marking call) change the question alone and the examples stay as written. The whole-text rewrites (translation, typos, casual writing, noise) run before the word-level steps (sensitive words, wording, tokenbreak), so they cannot undo a split, an encoded word or a code name (a fresh plan never pairs a translation with typos, casual writing or noise, which a kept plan may hold); the obfuscation numbers go in tens (translation 10 … ascii_art 90) so a family added later slots in between (noise took 35, wording 45, word_art 55, payload_split 65). A kept plan replays the order its manifest recorded: one made before this order applied the word-level steps first, one made before the first eval release the manipulation layer second (its plan file's `rules` id holds `layer_order`, so its resume warns; `resume=False` takes the new order). `run_chain(techniques, text, ...)` runs transforms inline and yields a generator's requests, capped at the technique's `max_tokens` and, with capture, tagged `{root}/{technique}/{n}` when the request's model can capture. Each technique gets the kwargs it takes (`gen_model`, `translate_model`, `check_model`, `benign_data`, `prompt_dir`, and `source_prompt`: the chain's input unless the caller gives one other than `None`, on which a selected fsh or dap variant picks its examples' subcategory before it inserts the finished question; in a kept plan where it runs first, that is the text it read before, unless a rewrite step ran before it, whose input it reads now) and its own `random.Random` seeded by `(seed, label, input id, iteration, technique)`, the label `jailbreak` or `variation`, so a replayed plan gives the same text within one version of the library (a technique whose code changed, as `to_ascii_art` with its cap, draws differently, and the plan file's `spec_version` need not move with it) and the two kinds draw apart. A step that changed nothing is recorded as `noop=<name>`; a step that leaves the text empty is a rejection (`reason=empty text`); the first rejection stops the chain. `combine_techniques(*fns)` and `apply_combination(fn, prompt, client=...)` run one prompt synchronously; manual chaining checks no rule.

**The stage** (`pipeline.run_augmentation`; front `generate_jailbreaks`). `resume_state` (lock, ledger keyed `(input_id, iteration)`), then the plan: kept on a resume (it is sampled) and checked against `<stem>.plan.json` — `planfile.changed_plan` compares the record less `pool`, `spec_version` and `rules`, and a changed seed, `rounds`, `family_weights` or `layer_rates` raises naming the keys and `resume=False`; the pool is compared apart (`_library_change`): techniques the library added after the plan's `spec_version` (a later `since`; a plan file without one was made at `"1.0"`) or retired after it (a later `deprecated`) are the library's change, and the plan is kept (a retired one it names still replays); any other pool difference (a section that adds or leaves out a technique, one no longer registered) raises as `pool`. Known limit: a section that newly names a family all of whose techniques came after the plan reads as growth and warns. The rules are compared apart too (`_rules_change`: today's `rules_id` of the plan's pool names and rounds against the plan file's, unknown in a plan file without `rules`). When the library added or retired techniques, or the plan's `spec_version` or rules are not today's, one WARNING (`_warn_since_plan`) names both versions, what was added and retired, whether the rules changed or are not recorded, and counts the pending units whose recorded combination `compatible()` now refuses or whose request obfuscation (the obfuscation right after the request, in every plan's order) keeps out another of its techniques (`after_request_obfuscation`; `_refused`, after the pass over the plan); it says the kept plan does not draw the added ones, runs those units as planned, and names `resume=False`, and when the rules changed or are not recorded, that each combination applies in the order it records (manipulation second in a plan drawn before the first eval release). A row records the plan's `spec_version` in `combination_spec_version`, not the library's (the run record holds that); a kept plan without a plan file, which records none, the library's. A plan without the file runs unchecked with a WARNING, and a WARNING counts the inputs the kept plan does not hold. Then benign data when a pending unit's combination has a `requires_benign` technique (`manipulation.get_or_generate_benign_data`: the pairs the cache in `Data_cache/benign/` lacks for the run's `benign_taxonomy`, one unit per `(main_category, sub_category, answer_type)` on the worker pool, up to 3 calls for a reply of 8 pairs, then each pair read by the check model (the stage's `check`, else the generation model; `jailbreak/benign_check`, given `category` (`<main> / <sub>`), `question` and `answer`, at `CHECK_TEMPERATURE`), a rejected pair asked for again alone with the verdict as feedback through `llm_pipeline.checked` (three generations of a pair in all, the reply's first; a reply that is not one pair rejected with no check call, `feedback.NOT_ONE_PAIR`), a pair rejected every time left out and counted in its unit's ack (`rejected_pairs`), so 9 to 43 calls a unit; with its own manifest and ledger and always resumed; a unit with no reply in the format, or none of whose pairs is left, is acked `rejected`, and a cache with no pair afterwards raises; a cache loaded as it is is not checked again; with `auto_generate_benign` off the cache is loaded as it is, and a missing one raises before any unit). A subcategory holds 8 pairs of each answer type, so the many-shot fsh/dap variants take their 32 short pairs across the cache (`pairs._many_pairs`: the chosen subcategory's first, then its main category's, then the rest, each group in `rng` order, each question once; a smaller cache gives all it has, its info adding `wanted=32`). 32 short pairs are about 1,200 tokens (four characters a token over the cached pairs; 1,450 at the 90th percentile), well inside the generation model's 10,000-token context. Input rows that share an id (one text without an id of its own, or an id given twice) are kept once, the last row, with a WARNING (`pipeline._one_row_per_id`), before the lock: planned twice they shared one ledger key, the first unit's row took the second's columns, and a run stopped between their saves lost the second; rows of one id under different entry types raise a `ValueError` naming the ids. Then `drive_units` over the pending units (`units.pending_units` builds a unit's generator only as the driver takes it; `pool_size(batch_size, client, check)` live). `generate_jailbreaks(check_model=None)` names the model that checks what a technique's model writes: the recipe's `check` (the jailbreak `Stage` calls the roles `gen`, `check` and `translation`), `None` the generation model, so no other model loads; the front creates its client only when a kind that runs draws a technique a check model checks, or one that needs the benign data, whose pairs it checks (`pool.uses_check_model`), the generation client standing in otherwise, `run_augmentation(check=)` hands its name through `unit_gen` to `run_chain` as `check_model`, a kwarg a technique may take, and the driver resolves the requests that name it.

**Typos** (`obfuscation/typos.py`) is its first user: `llm_pipeline.checked` has the generation model rewrite and the check model (`check_model`, else `gen_model`) read the rewrite against the prompt (`jailbreak/typo_check`, built with `PromptTemplate`, at `CHECK_TEMPERATURE`), a rejected rewrite made again with the verdict as feedback (`content_moderation.feedback.with_feedback`) up to `check_attempts` (2) rewrites; one still rejected returns `DISCARDED; reason=typo check failed; level=<level>; feedback=<verdict>`. `checked` takes a client or a model name for either model, as `extracted` does.

**Cognitive and persona** (`hacking/cognitive.py`, `_scenario_gen`, which `personas.py` shares) are its second: each attempt asks until a reply holds a scene (`extracted`, 3 replies), then the check model (`check_model`, else `gen_model`) reads the scene against the prompt (`jailbreak/scenario_check`: `original_prompt` and `scenario`; at `CHECK_TEMPERATURE`, read with `is_accepted`); a rejected scene is asked for again with the verdict as feedback up to `check_attempts` (2) scenes, and one rejected every time returns the prompt with `DISCARDED; reason=scenario check failed; feedback=<verdict>`, no construction call made. It is a loop of its own, not `checked`, since each attempt keeps its scene retries (`malformed scenario` stays the info of a scenario with no scene in 3 replies). A given `scenario` is neither asked for nor checked. A `record_scenario` given (the chain's, with the stage's `scenarios` on) is called with the scene the construction is built on, before it.

**Persuasion and tense rewrite** (`rewrite/preserve.py`, `preserved_rewrite_gen`) are its third, as typos is: `checked` has the generation model write the rewrite (`jailbreak/persuasion_rewrite`, given the entry's `technique_name`, `definition` and `example`; `jailbreak/tense_rewrite`, given `tense`) and the check model (`check_model`, else `gen_model`) read it against the prompt (`jailbreak/preserve_check`: `original` and `rewritten`; at `CHECK_TEMPERATURE`), a rejected rewrite made again with the verdict as feedback up to `check_attempts` (2) rewrites; one still rejected returns `DISCARDED; reason=preserve check failed; <label>; feedback=<verdict>`, `<label>` the info (`category=<key>` of the persuasion entry, `tense=<tense>`); an accepted rewrite with no text, or the prompt itself, returns `DISCARDED; reason=empty rewrite; <label>` or `unchanged rewrite`. `model_distractors` has a model write sentences for a `position` (`jailbreak/model_distractor`, `before` or `after`), asks again for a reply with no text, or that is the prompt (`extracted`, 3 replies, then `DISCARDED; reason=empty distractor`) and joins them to the prompt, which is not rewritten, with a space; no check model; info `position=<position>`.

`CommitBuffer` saves every 32 units. A row is the input's columns plus `sample_id` (`content_id` of the jailbreak text; an accepted adversarial no-op has its input's id, and the build leaves it out), `input_id`, `jailbreak`, `technique`, `technique_info`, `complexity`, `num_techniques`, `is_noop`, `accepted`, `reasoning`, `iteration`, `combination_spec_version` (the spec version its plan was drawn at). A unit that raises (on the async lane a too-long prompt too) gets an error row (the prompt unchanged, not accepted, `sample_id` `content_id("{label}:{input_id}:{iteration}")`) and is acked; on the grouped path a failed call stops the stage. The natural kind runs with `accept_noop=False`.

**Translation** (`obfuscation/translation.py`, 24 languages; Maori is left out, TranslateGemma inventing its terms, and Guarani, which measured below the acceptance bar) has two paths. Translation keeps its own checkers, which the stage's `check_model` does not reach (its own kwarg is `translate_check_model`, which nothing in the stage sets). A chat translator (`deepseek-v3.2` by name) translates and checks in each of up to 4 rounds, 2–8 calls, the verdict fed back. A machine-translation model (the `machine_translation` role, `translategemma-27b`) gets the text piece by piece, one request after another inside its unit: a paragraph, or a paragraph over 1,200 characters cut at sentence ends, each request capped at about three times its piece's tokens (1,536 at most). Each piece is checked at no model cost (empty; its GlotLID label among the language's accepted ones (an undetermined `und_*` label is no verdict, as without the detector); its length ratio, over the language's median, within 0.5 to 2.0, which a reply cut at its cap is not, for a piece of 20 characters or more (`MIN_BAND_CHARS`: a label or a digit keeps its characters); `MEDIAN_RATIO` holds each language's median measured with TranslateGemma 27B on the FLORES-200 devtest, 0.34 for Chinese to 1.31 for Scots Gaelic and Hmong; Scots Gaelic, Amharic, Hmong and Yoruba are on watch: Amharic's chrF++ is 9 points below NLLB-200 and the judge rejects 20% of Hmong's calls and 41% of Yoruba's), and a failing piece is resampled alone. When every piece passes, each is translated back to English and the generation model judges the original against the joined back-translation (prompt `jailbreak/translate_check_back`, 128 tokens), a rejection resampling every piece. Up to 4 rounds; the `DISCARDED` info names the piece (`piece=2/3`, `piece=all` for the judge) and why. Every request is the unit's own `LLMRequest` on the `drive_units` pool. `generate_jailbreaks`, when a kind's pool translates on such a model, renders `translate_mt` once before any call and raises unless it is one user message with the three markers in order (`check_mt_prompt`), and warns once when GlotLID is missing (`langid.available()`). Internals are captured under `{input_id}/{label}/attempt_{iteration}` and renamed to `{input_id}/{label}/{sample_id}` once the text is known. The `dialect` techniques (`obfuscation/dialect.py`, spec 1.4) run these two paths for a regional variant of a language: the machine translator is sent the variant's region or script code, and the checks use the base language's GlotLID labels and median ratio, so the language is checked and the region is not.

A row's variants are paired by position (`variants_of`): the values of each pool's `info_key` (`PoolRef.info_key`: `variant`, continuation's `style`, the decode hints' `hint`) go in order to the row's techniques that write that key, less those noted `noop=`; a row that does not pair up (rejected, error) counts none, but for an optional pool's key (`PoolRef.optional`, the decode hints, written at a rate), where a row without a hint counts none for that key and keeps its other variants. A fresh plan removes the table, and `_kind_files` clears it with the kind.

**The scenarios table** (`scenarios.py`; BELLS audit M2): with `generate_jailbreaks(scenarios=True)` (the `jailbreaks.scenarios` params key; off by default, both dataset types), each pending unit carries a `scenarios` list (`pending_units(scenarios=)`), `unit_gen` hands it to `run_chain(scenarios=)`, and the chain gives each technique that takes `record_scenario` (or `**kwargs`) a callable bound to its name; `cognitive._cognitive_gen` and `personas._persona_gen` call it once with the scene the construction is built on (the one the check accepted, or the one given), so a discarded scenario records nothing. `_row` puts the unit's scene rows (`rows_of`: `input_id`, `iteration`, the row's `sample_id`, `technique`, `scenario`) on its row under the private key `_scenarios`, which the save's `_append` takes off and appends to `<stem>.scenarios.csv` beside the manifest after the rows and before the acks. The table is not in the ledger's `_saved`: after the units `write_scenarios` keeps the rows whose `(input_id, iteration, sample_id)` the kind's CSV holds, the last of a repeated one (a save stopped between rows and acks runs its units again), writing it again through `write_concat` only when one goes, whether the run recorded scenes or not. A resume keeps the rows of earlier runs; a fresh run (`resume=False`) removes it, and `_kind_files` clears it with the kind. `technique_info` still names the category only; recording changes no row (a test runs the default attack pool both ways).

**The augmentation section** (`augmentation.py`): `generate_jailbreaks(augmentation=...)`, or a recipe's `augmentations`, is `{"adversarial": {...}, "natural": {...}}`. `resolve(section, kind, base=None, config_dir=None)` overlays a kind on its default from `configs/jailbreak/augmentations.json` (the `config_dir`'s when it has the file), with `base`, the dataset type's section, resolved over it, and checks it (every error names the kind and key; `_` keys are comments; the file's default kinds are checked when it is read, `_checked_file`: an unknown key of the file, a kind or its lists, which did nothing before, is left out with a WARNING naming the file, and a kind that is not an object or lacks a key (the group budget's aside), a missing or bad `natural_only_families`, or `exact_techniques` on the adversarial kind, which `kind_of` would read as natural, raises naming the file); a kind left out is the default, `null` switches it off. The stage runs `run_augmentation` once per kind that is on, with `technique_pool(resolved)` (the lists below, then only the techniques whose `kinds` hold the kind, which `pool.kind_of` reads as `rounds_of` does: natural when the resolved kind has `exact_techniques`, so the resolved dict carries no kind key; last, less every deprecated technique `techniques.allow` does not name, one it names being drawn with a `DeprecationWarning` and a logged WARNING (`_warn_retired`; Python shows the former only to `__main__`), for this release) and `rounds_of(kind)`: the **adversarial** kind (attacks) to `jailbreaks.csv`, the **natural** kind (natural variations) to `variations.csv` (beside `output_path` when one is given, else `paths.variations_csv(data_dir)`, unless `variations_path` says otherwise); each file has its own manifest, plan file, ledger, coverage table and variants table. A kind whose `entry_types` match no input, or whose pool is empty, warns and writes nothing.
- Keys of both kinds: `entry_types` (`null` all), `translation` (bool), `layers` (`deny`, `[]` in both packaged kinds; `allow`, the layers off by default to turn on), `families` and `techniques` (`allow`, `deny`; `allow` `null` is everything), `pure_only`, `family_weights`, `iterations`. Adversarial only: `max_complexity`, `max_obfuscations`, `layer_rates` (`rewrite`, `hacking`, `manipulation`, `requests`, `request_obfuscation`, over the spec's), `allow_request_obfuscation`, `budget` (`"unit"`, the default, or `null`; or `"group"`, the group budget above) and `max_unit_complexity` (its ceiling, default `max_complexity + 3`; only with `"group"`, at least `max_complexity` and every round's; both are kind keys, a round may not name them, and the natural kind refuses them), `rounds` (`null`; `"escalation"`; or a list of rounds, which sets `iterations`). Natural only: `exact_techniques` (default 1).
- **Overlay**: a value replaces the default's whole value, lists included, except `layers`/`families`/`techniques`, whose `allow` and `deny` overlay one by one; a `deny` given alone also takes its names out of the default's `allow`. After the overlay `_deny_layers_off` adds each layer of `layers_off_by_default` (`rewrite`) to `layers.deny` unless `layers.allow` names it, so the pool and `rounds_of` read one list and a kind's own `layers.deny`, or a `config_dir` copy of `augmentations.json` saying `"deny": []` or `["rewrite"]`, leaves the layer off; `layers.allow` is a list (`[]` for none) that may name only such a layer (one on already raises, saying to take it out), a layer under both lists raises, and the resolved kind keeps `allow` only when one was given, so a kind without it (both dataset types') resolves as before (the flat `include_<layer>` keywords toggle the resolved deny list and keep the layer off). The natural kind must keep an allow list. An allow list or `family_weights` naming a family or technique of a layer the kind leaves off raises when the layer is off by default (`rewrite` without `layers.allow`; the message says to write `"layers": {"allow": ["rewrite"]}`), since the pool would drop it without a word, and a kind naming nothing else would draw nothing; one of a layer the kind's own `layers.deny` names is dropped with a WARNING (an eval run denying `hacking` drops the eval lists' `framing`), and a `family_weights` entry of it raises (`_check_denied_layers`). An allow list naming a family or technique whose spec `kinds` lack the kind raises (`_check_kinds`; a `config_dir` copy of the former `augmentations.json`, whose natural `families.allow` named `structural`, `temporal` and `continuation`, does), naming it and the fixes: take it out; for a technique, add the kind to its spec `kinds`; for a family, list under `techniques.allow` those of its techniques the kind draws, which the message names (a family's `kinds` apply to every technique in it that sets none of its own, so adding the kind there is not offered). `natural_only_families` (`casual_writing`) are added to the adversarial `families.deny` unless its `families.allow` names them; a family whose spec `kinds` are `["natural"]` alone (`smalltalk_prefix`, `smalltalk_suffix`, `benign_role`) needs no entry there, since no attack may draw it.
- **Translation** has its own switch: no family list changes it (`layers.deny`, `techniques.deny` and `pure_only` still apply). On, it admits the whole family unless `techniques.allow` names some of its techniques (`pool.languages()`): then only those. Off, the translation and the dialect an allow list or `family_weights` names are left out of the resolved kind with a WARNING (`_switch_off_translation` handles the `dialect` family exactly as translation; an allow list it empties becomes `null` beside the other, and a kind that allowed only translation or dialect raises), so `"translation": false` overrides the eval type in one key. The packaged adversarial kind has it `true` (the attacks draw all 24 languages and, since spec 1.4, the six `dialect` variants, both on the local `translategemma-27b`), the natural kind `false`; a run without a GPU sets `"adversarial": {"translation": false}` or names `deepseek-v3.2` for translation. With the switch on, an allow list admits the whole translation family unless `techniques.allow` names languages, and the dialect family with it unless `techniques.allow` names dialects, so a kind that names its own languages (the eval type) gets only those and no dialect, and the packaged natural kind draws the six dialects when the switch is on without naming `dialect`. `resolve_role` plans the translation model only when a kind's pool has a translation or dialect technique (`uses_translation`: the translation family and the dialect family (`pool.DIALECT`, spec 1.4), both run on the same model, gated by the same switch and auto-added to an allow list the same way; a rewrite technique, as any other that calls a model, calls the generation model, and the rewrite layer adds no role, a test holds it for both dataset types).
- Defaults: both kinds leave the `rewrite` layer off (the spec's list): its 16 techniques are in no default pool, and all say `["adversarial"]`, so the natural kind never draws them. To turn it on for the attacks a kind writes `"layers": {"allow": ["rewrite"]}`, which adds the 16 to its pool (301 techniques in 37 families for the packaged adversarial kind; `eval.json` allows named families, none a rewrite family, so its pool and rounds stay as they were even then) and, for budget rounds, its `layer_rates` give `rewrite` a rate above 0 (`_warn_rewrite_rate` logs a WARNING for a budget round at rate 0 in a kind that draws the layer, and for a rewrite rate above 0 while it is off; `"rounds": "escalation"` carries the kind's `layer_rates.rewrite` into its two budget rounds, whose own rates replace the kind's); a count round draws a rewrite technique its pool holds, whatever the rate. Every section plans as before: a kind that leaves the layer off has rounds without `include_rewrite`, so no kept plan changes. The rounds of a kind whose pool holds a rewrite technique say `include_rewrite: true` (written only then), and an adversarial plan made with the layer allowed before its pool held one, with no `include_rewrite`, raises on resume naming `rounds` (take `rewrite` out of its `layers.allow` to keep the plan). The adversarial kind denies no family (only `natural_only_families`): 285 techniques in 34 families, the 24 translations and the six dialects among them; its `allow_request_obfuscation` is true, which adds the key to its rounds, so an adversarial plan kept from before it was turned on (its section leaving the key out) raises on resume, naming `rounds` (run the kind once with `resume=False`). The natural kind allows the families `typos`, `casual_writing`, `noise`, `neutral_container`, `answer_language`, `answer_format`, `asking`, `indirect`, `smalltalk_prefix`, `smalltalk_suffix`, `benign_role`, and (spec 1.4) `transliteration`, `code_switching`, `romanization` (not `dialect`, which the translation switch auto-adds like the translation family) and the techniques `to_leetspeak_basic`, `to_adversarial_suffix_punctuation`, `to_adversarial_suffix_emoji`, and denies three answer-format directives; with the `kinds` gate its pool is 96 techniques in 16 families (typos low and medium, the nine casual writings, the eight low and medium noise techniques and the six neutral containers (spec 1.2), the twenty-six answer languages (six since spec 1.2), the four neutral answer formats, asking's three (the urgent ask since spec 1.3), indirect, small talk before and after, the three benign roles (spec 1.2, natural only), those three suffix and leetspeak techniques, and the spec 1.4 language-mix families drawn without the translation switch (the four transliterations, the ten code-switching techniques, the ten romanizations)), the 24 translations and the six dialects joining with its switch on (126). The pool changed four times. `structural`, `continuation`, `temporal`, the high and insane typos and the dialogue and story formats left the natural kind when the `kinds` gate came in: a natural plan made before the gate raises on resume (its pool changed; run the natural kind with `resume=False`), and the build leaves out its benign variations made with them. Spec 1.2 then grew the pool: a natural plan made after the gate and before spec 1.2 resumes with the growth WARNING and does not draw the noise, the neutral containers, the six new answer languages, small talk or the benign roles until planned again with `resume=False`. Spec 1.3 then added one, `to_ask_with_urgency`: a natural plan kept from before it resumes with the growth WARNING naming it, and a fresh one may draw it. Spec 1.4's language-mix step then added the four transliterations, the ten code-switching techniques and the ten romanizations (the six dialects too, but only under the translation switch): a natural plan kept from before resumes with the growth WARNING naming them, and a fresh one may draw them.
- The twelve flat keywords (`include_*` ×5, `pure_only`, `max_complexity`, `max_obfuscations`, `sampling_probs`, `iterations`, `settings_per_iteration`, `entry_types`; `FLAT_KEYWORDS`) are deprecated aliases into the adversarial kind for one release, each with a `DeprecationWarning` (`apply_flat_keywords`), wherever they are written: `generate_jailbreaks` keywords, the flat form of a recipe's `augmentations`, or `params["jailbreaks"]`.

**Reference list coverage:** benchmarked against 73 instruction primitives + 74 request primitives; every feasible one is covered. Left out by design: `agent_context_additional_instr` (needs the system prompt), `fine_tuning` (out of scope), `use_highly_specialized_language` (no clear way to build it), `direct_question` (changes nothing). Beyond the list, ported from the BELLS_Jailbreak reference library (its `hacking.py`, `manipulation.py` and `obfuscation.py`, as the module docstrings of this repository's first commit say): ASCII art, adversarial suffixes, structural wrapping, cognitive hacking, manipulation (FSH, DAP), the encodings morse and braille, the translations into Zulu, Scots Gaelic, Bengali and Javanese, and, from its `guardrail_attacks` (BELLS audit M3, M4), letter spacing (`space_between_letters`) and the guardrail address (`benign_instruction_for_classifier`, its three formats). Also beyond the list: continuation attacks, indirect embedding, casual writing, noise (random capitals, scrambled letters, keyboard typos, emoji), neutral containers (a code comment, a YAML document, a CSV row, an email, a transcript line, a log entry), small talk and benign roles (natural variations only), many-shot FSH and DAP (32 pairs, spec 1.2), the persona templates, the fake turns, three answer formats (dual answer, tagged prefix, answer in an encoding) and seven members of the thin request families (spec 1.3), the encodings rot18, rot47, ASCII ordinals, reversal (characters, words, word order), Caesar, Atbash, look-alike letters, zero-width noise, hex, binary, URL percent-encoding, HTML entities, base32, base85, fullwidth and math-styled Unicode, four answer formats (code, dialogue, story, structured data), and those four languages as answer languages, with Hmong, Guarani, Chinese, Hindi, Yoruba and Amharic (spec 1.2).

**The combination search** (`search.py`; `search_combinations`, exported from `redact` and `redact.jailbreak`; not a recipe stage, called from Python like `multi_turn`) is a beam search over single-turn combinations against a safety-trained **target** model, scored by a **judge** (the `multi_turn.evaluate` pattern, `SUCCESS_JUDGE_SYSTEM` by default, read with `is_accepted`). Per input, round 0 draws `width` valid combinations with the library's own sampler (`sample_combination` over `applies`'d techniques, so every draw is compatible); each later round keeps the `beam` best (only candidates that applied, never the identity or a discarded/error row, by score then fewest techniques then a seeded draw: with 0/1 scores a seeded pick among the smallest, breadth-first) and **mutates** them (add a compatible technique, swap one for another of its family, drop one — each checked with `rules.compatible`, so never an invalid pair, and kept within round 0's budget), at most `max_candidates` per input per round (8 by default, a seeded sample over the parents and add/swap/drop kinds; `None` tries all — about 900 per input over the default pool), up to `depth` rounds or until the judge says success (`stop_on_success`). A candidate is applied with `run_chain` and driven on `drive_units` like the stage, the result sent to the target, the reply judged. It writes `Datasets/jailbreak_search.csv` (one row per tried candidate — the rows are the tree — each with `sample_id` = `content_id("search:{input_id}:{round}:{candidate}")`, `input_id`, `round`, `candidate`, `parent`, `applied`, `jailbreak`, `success`, `score`, `rules`, ...) and returns `{"best": {input_id: BestCombo}, "rows": df}` (`best_combinations`, `search_tree` read a saved frame). It follows the resume model (`Manifest`, `Ledger` keyed `(input_id, round, candidate)`, `resume_state`, `CommitBuffer`, a `<stem>.plan.json` that a changed seed/width/beam/depth/max_candidates/pool/rules/target/judge/system/stop_on_success resume raises on); a round's plan reads only the rounds before it, so a kill mid-search (even after a success is saved mid-round) resumes to the same rows with no duplicates; a prompt too long on the async lane is a failed row, not a crash. Requires-benign techniques are dropped from the pool unless `benign_data` is given, and the module imports `augmentation` lazily so it adds no import cycle. `docs/stages/combination-search.md` and `docs/internals/jailbreak.md` have the details; `scripts/search_smoke.py` runs it on a pod against the local debug model (counts only).

### `content_moderation/` — Content Moderation Generation

Three stage cores, each called by its front in `stages.py`:

- **Inputs** (`InputPipeline.run_from_constitution`, `inputs.py`; front `generate_inputs`), seeded from the constitution in every run. An entry is checked against its `source_category` (a benign-taxonomy category for the general-benign part), and its `source_taxonomy` is copied onto its rows when the constitution has the column. Each constitution entry is `samples_per_entry` units `(entry, iteration)`, each its own generator on the `drive_units` pool (its generation and check go on the async lane, units finish apart): one generation call for one sample written to the unit's spec (`{sample_spec}`), made again for a reply without its `[END]` marker (`constitution.parse.strip_end_marker`) or with another count (`expected_count=1`; up to `max_attempts`; rejected whole, never salvaged; the replies without the marker are counted in a WARNING), then one check call with the entry-type-aware `build_quality_checker`, at temperature `CHECK_TEMPERATURE` (0.15; the generation at the model's default). A rejected sample is saved with its reason; a unit rejected on every attempt is acked `rejected` with no row, and so is one whose generation or check prompt is too long, on the async lane (on an Anthropic or introspection binding that stops the stage); a unit whose sample the folder holds already is acked `no_sample`. No earlier sample enters a generation prompt; a text is written once per folder, a repeat dropped after generation by its content id. Rows go to `Datasets/constitution_inputs/{category}/samples.csv` (`SAMPLE_COLUMNS` plus `source_sample_description`, `constitution_category`, `source_group_tag`, `source_taxonomy` when the constitution has it, `iteration`, and a column per dealt axis: `length`, `register`, `writer`, `framing`, `directness`, `focus`), from the one template `prompts/input/generation/template.json` (overlaid by `prompt_dir`; the spec's labels and hints live in `configs/generation_axes.json`). The ledger `constitution_inputs.state.jsonl` is keyed `(sample_description, entry_type, iteration)`, an ack holding `ids` and `accepted` (or `status` and `attempts`) and the unit's `spec`; a manifest row adds `category` and `spec`. On a resume a done unit keeps its ack's spec (`deal_specs(..., fixed=)`, as the outputs' modes), so the manifest and the coverage agree with the rows; an ack without one, or a key two entries share, is dealt again. `constitution_inputs.plan.json` holds one record (`seed`, `samples_per_entry`, the axes' weights) and stops a resume of a folder with done units that would deal another plan, naming `resume=False` (a folder with no done unit is not compared, and its record is written anew; the outputs stage compares on every resume); a `samples_per_entry` that is not a whole number of at least 1 (`check_samples_per_entry`) raises before anything is written (the front and `load_params` check it too); `constitution_inputs.coverage.csv` joins the manifest's specs to the acks. A folder whose ledger acks units without an `iteration`, or whose files lack `iteration` or an axis column, stops before any call. `resume=False` starts the whole stage over (the tree, its `.cut` and `.tmp` files, the ledger and the manifest), an empty frame too. An inputs folder written when a `style` picked one of two templates is not supported: start a new `data_dir`. An entry whose `(sample_description, entry_type)` an earlier one has (the key holds no category) is left out with a WARNING. Before anything is cleared or called, every `source_category` must name a folder (`check_category_name`), the generation and check prompts are rendered once with empty values (a broken overlay stops the run there), and a category file without `source_taxonomy`, when the constitution has it, stops the run. It returns a `ConstitutionInputResult` (totals).
- **Outputs** (`run_output_generation`, `outputs.py`; front `generate_outputs`). `outputs_per_input` (k; 1 by default, 2 in the `training` type) `llm_pipeline.checked` units `(input_id, iteration)` per input row, each a row, each dealt an **answer mode** (`modes.py`): `harmful` or `helpful`, from the modes `outputs.modes` allows its input's entry type, over `DEFAULT_MODES` (`harmful` → harmful; both dual-use types → both; `benign` → helpful; a frame without an `entry_type` column is answered as `harmful` with a WARNING; a missing, NaN or empty cell in the column, and an entry type the mapping lacks, raise before anything is cleared, naming the inputs: a label is never guessed). `deal_modes` deals them per `(category, entry_type)` group from one `Dealer`, as `deal_specs` deals specs, an input's units taking a mode at most `ceil(k / modes)` times (from k = 2 a dual-use input gets one answer of each; at k = 1 a dual-use group alternates). The mode picks the generation prompt `output/generation/<mode>` and the checker `build_output_quality_checker(category, mode)` (`output/quality_check/<mode>`, shown the category, not the entry type; they differ in the mode's semantics line: the harmful one asks that the response contain the harmful content requested, the helpful one for a normal, helpful answer to the request as asked; a refusal is rejected in both), both read and rendered once with empty values, and every `(category, mode)` checker built, before `resume_state`. With the checker on, a response under `MIN_RESPONSE_CHARS` (20) characters once its code-fence marker lines are removed is rejected without a check call (`checked(precheck=)`; `rejection_reason` `feedback.TOO_SHORT`, "too short: ..."); `check_outputs=False` has no floor. The check calls run at `llm_pipeline.CHECK_TEMPERATURE` (0.15: verdicts far more repeatable at the same acceptance), the generations at the model's default. `max_attempts > 1` regenerates a rejected response with the verdict (or that reason) as feedback. On the async lane an input whose generation or check prompt is too long gets a rejected row with an empty response; on an Anthropic or introspection binding the stage stops. Each unit is then dealt one spec of the response axes (`{response_spec}`; the checker is not shown it), with its real iteration, so an input's siblings differ on every axis none of whose values weighs over 1/k. Writes `output_responses.csv` (`input_id`, `input_prompt`, `category`, `subcategory`, `entry_type` (the input's), `model`, `source`, `sample_id` (an error row's `content_id("{input_id}:{iteration}:prompt too long")`), `output_response`, `accepted`, `rejection_reason`, `iteration`, `response_mode`, `output_label` (`harmful` or `benign`, `OUTPUT_LABEL`), `response_label` (`<entry_type>_<output_label>`, `response_label()`; split on the last underscore only), then `response_length`, `response_format`, `response_register`), ledger keyed `(input_id, iteration)` (an ack holds `mode`, `spec` and `accepted`; on a resume a done unit keeps its ack's mode and spec, passed to `deal_modes(..., fixed=)` and `deal_specs(..., fixed=)`, which deal the other units around it, so the manifest and the coverage agree with the rows; an ack without them, or the spec of a key two input rows share, is dealt again), a manifest row with `iteration`, `category`, `entry_type`, `mode` and `spec`; a ledger with an ack without `iteration` (read through a ledger keyed on `input_id`), or a file without `iteration` and the mode columns or without the response columns, stops a resume before any call, before the plan file's check; `output_responses.plan.json` (`seed`, `outputs_per_input`, `modes` (the whole mapping), the weights) stops a resume that would deal another plan; `output_responses.coverage.csv` as the inputs', plus a row `axis` `mode` per mode a group was dealt (written without axes too). The front caps inputs per `(category, entry_type)` with `max_per_category` (`take_per_group`), then with `max_samples`, both counting inputs before the expansion. Two siblings with one text are two rows with one `sample_id` (no stage dedup; the build compares only across parts).
- **Paraphrase** (`run_paraphrase_target`, `paraphrase.py`; front `generate_paraphrases`). `k` paraphrases per base input, and per accepted base output (`accepted_mask`) when `target` names the outputs (default `inputs`, `DEFAULT_TARGET`; a run without the outputs target warns once when `paraphrases_outputs.csv` holds rows an earlier run left, which the build still merges); a unit is `(input_id, iteration)` for the inputs target and `(response_id, iteration)` for the outputs target (`response_id` the response's `sample_id`, since an input may have several responses; the row and the ack keep `input_id`, the input answered, which the eval build and `exclude_from` rely on), and gets a paraphraser from `paraphrase_pool(paraphraser)` (`"distribution"` is every `paraphraser`-role model; each must be registered, `get_model_config` in the front stopping an unregistered one before anything is cleared) by a seeded hash of its id; a row's and a manifest row's `category`/`entry_type` are empty where the source has none, never `nan`. A paraphrase of a response always carries `response_id`, `response_mode`, `output_label` and `response_label` (copied, empty when the source lacks them), so it has its response's label. A resume of the outputs target onto a folder written before (an ack without `response_id`, read through a ledger keyed on `iteration`; or a file without those columns) stops before any call, naming `resume=False` for the target and a new `data_dir`. The paraphrase prompt is `paraphrase/generation/<model>` when it exists (overlay, then packaged), else `paraphrase/generation` (`paraphrase_prompt`); the sample is stripped, and a paraphrase equal to its stripped original is dropped; a paraphrase prompt with a `fingerprint` key is checked for every paraphraser of the pool at the stage's start, before any client (`check_paraphrase_prompt`, as `check_mt_prompt` is; the humanizer's pins the card's format). Five gates run first, in code (`GATES`, `gate_reason`: length, the squeezed paraphrase within 0.5x to 1.5x + 20 characters of the squeezed original; split, a single-line original of 35 words or fewer stays on one line; script, under 10% of the letters in scripts the original lacks; language, GlotLID labels differing at 0.9 or above on both, skipped without the `langid` extra, which the front warns about once; artifact, an HTML tag or a rule line the original lacks): a gated paraphrase is saved rejected with its reason and no check call. Then a separate checker (`build_paraphrase_checker`, the strict prompt; by default on the `uncensored_gen` model; the front warns when it is also a paraphraser), at `CHECK_TEMPERATURE` 0.15, rejects a paraphrase that answers, adds or drops content, or changes the language or the meaning; `check=False` runs neither. A text under `min_words` words (12, `MIN_WORDS`; `skip_reason`) gets no paraphrase: its unit is acked `skipped` (with `reason` and `min_words`) with no call and no row, the manifest marks it, the run record counts `skipped` per reason (`_paraphrase_skipped`), and on resume the ack wins whatever the threshold (a WARNING counts the units the current one would send). A duplicate, empty or unchanged paraphrase is dropped (with the check on, found by the unit's precheck before any check call); every attempted unit is acked, a dropped one too (`dropped_dedup`). Writes `paraphrases_inputs.csv` / `paraphrases_outputs.csv`. It runs one paraphraser at a time; each paraphraser's units run on the `drive_units` pool (`llm_pipeline.checked`, the gates as `precheck`), with a reply cap per unit (`reply_cap`: 2.5 times the original's tokens at 3 characters a token, plus 32, rounded up to a power of two from 64, at most the model's `default_max_tokens`; cut replies are expected, and the length gate catches most of them with the check on), saved every 32 units and after each paraphraser's units, before the next is loaded; on the async lane a too-long prompt acks its unit `prompt_too_long` with no row; of two units with one paraphrase, the first to finish keeps its row; when the pool's models cannot be resident together, it releases their engines between them. The default paraphraser is the humanizer 12B; `venice-paraphraser` (the generator's own weights) holds no role and runs when named; the trained defingerprinting model lives in another repository.

**The generation axes** (`axes.py`, `configs/generation_axes.json`, a `config_dir`'s when it has one): an `inputs` section (`length`, `register`, `writer`, `framing`, `directness`, `focus`, and `domain`, shown from the entry's subcategory) and an `outputs` one (`length`, `format`, `register`), each value with a `label`, a one-sentence `hint`, a `weight` and optionally `not_with`, each axis with a `dimension`. `resolve(stage, given, *, weighting="table", config_dir=None)` overlays the `axes` param (`{axis: {value: weight}}`, an axis `null` left out, `False` none), then with `weighting="log"` (a front's `axes_weighting`; the `training` type's inputs) weights each value of weight w above 0 by 1 + ln(w / m), m the axis's least weight above 0, normalised per axis: a weight of 0 stays 0, an axis with one value above 0 is unchanged, and the plan file records the weights dealt, so a resume with another weighting raises. `deal_specs(axes, units, *, seed)` deals one spec per `(group, (entry, iteration))` unit, per `(category, entry_type)` group in `(entry, iteration)` order from one `Dealer`, each unit's rng seeded by `(seed, *group, entry, iteration)`, so the plan does not depend on input order; an entry of k units takes a value at most `ceil(share × k)` times, so its siblings differ on every axis none of whose values has more than 1/k of the weight. `render_spec` writes `Label: value label — hint` per axis; `spec_columns` the row's columns (`response_` prefix for outputs); `write_stage_coverage(axes, manifest, ledger, *, extra=())` the coverage table, planned from the manifest and accepted from the acks, `extra` naming manifest fields counted as axes of their own (the outputs' `mode`), removed without axes and without anything of `extra`. The deal is recomputed every run (a pure function of the plan file's keys and the sorted units), `fixed` giving the done units the specs their acks record (a spec that no longer fits the axes is dealt again); `write_stage_coverage` counts an accepted unit under the spec its ack records. `focus.mixed` is at weight 0: `focus` is undecided against `request_shape`, `container` and `example_priming`, and `check_dimensions` would stop a run dealing it beside them. Paraphrase rows carry no axis columns, by design (a paraphrase of a response copies its answer-mode columns, which are its label).

`checker.py`'s builders return `(original, sample) -> messages`, the contract of `llm_pipeline.check`, each loading its prompt once as a `PromptTemplate`. `feedback.py` gathers the prompt text the stages add at run time (rejection feedback, `TOO_SHORT`, the length floor's reason, and `NOT_ONE_PAIR`, a benign pair asked for again that is not one pair); it moves to prompt JSON later.

### `constitution/` — Constitution Generation

Structured category hierarchies for constitutional classifier training, at 4 severity levels:

1. **Absolutely harmful** (`harmful`) — clear-cut violations, always flag
2. **Dual-use harmful** (`dual_use_harmful`) — borderline, harmful framing
3. **Dual-use benign** (`dual_use_benign`) — borderline, benign framing, could look harmful
4. **Absolutely benign** (`benign`) — clearly safe, never flag (hard negatives)

`ConstitutionPipeline(client, output_dir=None, prompt_dir=None).run(taxonomy, ...)` (front: `generate_constitution`, role `constitution_gen`, `claude-opus-4-6` by default) makes one call per **unit**: a `(source_category, entry_type)` pair for each of the first `num_taxonomy_categories` taxonomy categories and each entry type (all four by default, or `entry_types` in their order), asking for `num_categories` constitution categories, plus, with `include_general_benign` (on in both dataset types), one unit per category of the first `num_taxonomy_categories` of `benign_taxonomy` (the recipe's, passed by the run; default `benign.json`, 11 categories), through the `general_benign` prompt with the same kwargs a taxonomy unit gets (`Category`, `description`, `subcategories`, `group_tag`, `num_categories` = `general_benign_categories`, 10). A `Unit` has `prompt` (its folder under `prompts/constitution/`, the entry type unless given) and `source_taxonomy`; its key is `source_category::prompt`. `plan_units` raises before any call for a planned category that cannot name a folder (`check_category_name`) and for `include_general_benign` with a benign taxonomy of no category. A general-benign unit's rows are `entry_type` `benign`, `source_category` the benign category, `source_taxonomy` `benign` (taxonomy rows say `harmful`). The front reads the former names `include_standalone_benign`/`standalone_benign_categories` for one release with a `DeprecationWarning` (given, they win). `units.py` plans the units (`plan_units`), builds each call from `prompts/constitution/{prompt}/` (`messages_of`) and turns a reply into rows (`rows_of`, via `parse.parse_constitution`). A reply without its `[END]` marker (stopped at the token limit or by a provider filter) or with no entry that parses is rejected whole and the call made again, up to 3 attempts (`llm_pipeline.extracted`); a unit rejected every time is acked `rejected` with no rows, skipped on resume and named in a warning. The units run one at a time (`drive_units(pool_size=1)`); a failed call, or a too-long prompt on any backend, stops the run and the units saved before it stay acked.

Rows (`sample_id` = `content_id(sample_description)`, `constitution_category`, `constitution_subcategory`, `sample_description`, `entry_type`, `source_category`, `source_taxonomy`, `source_group_tag`, `model`) go to `{entry_type}.csv` (`general_benign.csv` for a benign-taxonomy row, `units.file_of`) and `merged.csv` under `Data_cache/constitution/`, saved per unit through `CommitBuffer(every=1)` before the unit's ack; a resume of a `merged.csv` without one of these columns raises before any call, naming `resume=False`. The plan is `constitution.manifest.jsonl` (`source_category`, `entry_type`, `prompt`, `status`), the ledger `constitution.state.jsonl`, keyed `source_category::prompt`, records every CSV's size with each save: `resume_state(artifact=<folder>, pattern="*.csv", units_in=)` locks the stage, checks every CSV and cuts back what an unfinished save left (a torn row, or rows before their ack), so the unit runs again and no row is torn or written twice; a CSV missing or changed stops it, naming the remedies; a folder without sizes (no ledger, or the plain one an earlier version wrote) is taken over once, a unit with rows in `merged.csv` counting as done. `merged.csv` keeps every saved row, so a resume with fewer categories keeps the others' rows, and the inputs stage seeds from all of them. `resume=False` removes the CSVs, the ledger and the plan first. `run()` returns `read_constitution(output_dir)`: `merged.csv` with every cell as text and an empty one as `""` (an empty frame with the columns when there is none), rows of earlier runs included; the driver reads the constitution the same way to seed a run's inputs.

## Prompt JSON Schema

All prompts are `.json` files in `src/redact/prompts/{pipeline}/{category}/`, loaded at runtime via `load_prompt(pipeline, category)` in `llms/prompting/prompts.py`, which resolves to the single `.json` in that directory, else `template.json`.

**`prompt_dir` is an overlay, not a replacement.** Each prompt is read from the user's directory if present and from the packaged tree otherwise, so customizing one checker means copying one file, and the rest keep the library's later improvements. `report_prompt_sources(prompt_dir)` logs the resulting picture once at startup (what is overridden, and any directory matching no packaged prompt); a per-model paraphrase prompt of a registered model is an override, not unused (`per_model`). `scripts/scaffold_prompts.py TARGET` writes an editable starting tree: real prompts by default, `--empty` for TODO skeletons whose key set mirrors each real file's; it refuses to write over a file the folder holds unless `--overwrite`. Pipelines: `constitution` (one per entry type, plus `general_benign`), `input` (`generation`, `quality_check`), `output` (`generation/{harmful,helpful}`, `quality_check/{harmful,helpful}`: one per answer mode), `paraphrase` (`generation`, `generation/<model>` for a paraphraser with a prompt of its own, `check`), `jailbreak` (per technique step: `scenario_generation`, `persona_invention`, `persona_scenario_generation`, `persona_construction`, `jailbreak_construction`, `payload_split_semantic`, `extract_harmful`, `benign_generation`, `category_selection`, `rewrite_with_typos`, `typo_check`, `scenario_check`, `persuasion_rewrite`, `tense_rewrite`, `model_distractor`, `preserve_check`, `synonym_substitution`, `pseudonym`, `word_game`, `translate`, `translate_retry`, `translate_check`, `translate_mt` (the machine-translation format, no system prompt), `translate_check_back`, `code_switch`, `code_switch_check`, `romanize`, `romanize_check` (the language-mix techniques' rewrite and meaning check: few-shot turns that mirror the template, a verdict-first reply for the checks)), `conversation` (`judge`, `pair_attacker`, `success_judge`), and `format_instructions` (`numbered`/`structured_qa` — not a chat prompt, a `{"instruction": "..."}` snippet `PromptTemplate`'s `format_style=` appends to another prompt's `system_prompt`). The tree also holds `input/category_check`, which no code loads yet.

```json
{
  "system_prompt": "... {Category} ...",
  "template": "... {sample} ...",
  "seed_fields": ["Category", "sample"],
  "few_shot_examples": [],
  "metadata": {
    "version": "1.0",
    "notes": ""
  }
}
```

A prompt file carries no `category` or `pipeline` field: its directory is its identity. `build_messages(prompt_config, **kwargs)` renders both `system_prompt` and `template` with the same kwargs (via `str.format_map`), so any placeholder works in either field; `seed_fields` documents the placeholders and nothing reads it. Some prompts carry extra keys the code reads (`level_descriptions` for the typo rewrite, `answer_styles` for benign generation).

## Usage

Every stage front but `build_dataset` takes one **`data_dir`** working root, a **role-defaulted model** per role (`None` is the registry role's default: constitution → `constitution_gen` (Claude Opus), generation and checking → `uncensored_gen`, translation → `translation` (`translategemma-27b`, local), paraphrase → `paraphraser` (`humanizer-12b`, local)), `prompt_dir`, and **`resume`** (default `True`). A model name resolves through the registry (`llms/model_config.py`) to a `ModelClient`; for a custom endpoint, `register_model()` it.

```python
from redact import (
    generate_constitution, generate_inputs, generate_outputs,
    generate_jailbreaks, generate_paraphrases, build_dataset, run_pipeline,
)

DATA_DIR = "./runs/training"

# Inputs are seeded from a constitution (eval and training alike); they land in
# Datasets/constitution_inputs/. Without constitution_df, the saved one is read.
constitution = generate_constitution(data_dir=DATA_DIR, num_taxonomy_categories=3)
inputs = generate_inputs(data_dir=DATA_DIR, constitution_df=constitution, samples_per_entry=3)

outputs = generate_outputs(data_dir=DATA_DIR, inputs=inputs, outputs_per_input=2)  # two responses per input, each in an answer mode, checked
jailbreaks = generate_jailbreaks(data_dir=DATA_DIR, inputs=inputs)  # attacks + natural variations, defaults
# A changed section plans the kind again: resume=False starts it over (a resume would raise).
jailbreaks = generate_jailbreaks(data_dir=DATA_DIR, inputs=inputs, resume=False, augmentation={
    "adversarial": {"entry_types": ["harmful"], "rounds": "escalation"},
    "natural": None,                         # off: variations.csv is left as it is
})
paraphrases = generate_paraphrases(data_dir=DATA_DIR)  # inputs; target="both" adds the outputs
dataset = build_dataset(data_dir=DATA_DIR, mode="training")         # paraphrases merged in

summary = run_pipeline("src/redact/configs/runs/training_example.json")   # or scripts/run.py
```

`build_dataset(mode="eval")` writes no complete dataset: `eval_inputs.csv` (inputs, then their paraphrases marked `paraphrased`), `eval_outputs.csv` (responses, then their paraphrases when the outputs were paraphrased) and `eval_jailbreaks.csv` (the attacks that changed their input, `is_jailbreak` true, then the bare benign inputs), each with `sample_id`, `text`, `label`, a fixed set of provenance columns and the generation axis columns (`docs/stages/build.md`: an input's six, `length` to `focus`, in every file, taken from the input on a response or an attack, and a response's three, `response_*`, in `eval_outputs.csv`; empty on a paraphrase; `eval_jailbreaks.csv` has `families` and `layers` after `technique` since the release of spec 1.4): `label` is the entry type in `eval_inputs.csv` and `eval_jailbreaks.csv`, and `<entry_type>_<output_label>` (the response's `response_label`; a paraphrase's is its response's) in `eval_outputs.csv`, which also has `output_label`; an output or paraphrase file written before the modes falls back to `entry_type`, with one WARNING per part. `exclude_from` (the `build` params key, eval only) names a training run's folder or files: an eval row whose id or normalised text they hold is left out with the rows derived from its input; a row whose input's constitution description they hold is kept and flagged with a warning. Both are counted in `Datasets/eval_excluded.json` and the build record's `counts.excluded` (`exact` and `normalised` are rows removed; `descriptions` is rows kept), and the files read are among the record's `sources`. A folder of `exclude_from` with a byte-identical `Data_cache/benign/benign_samples.csv` is warned about. The `*_path` overrides (`output_path`, `variations_path`, `manifest_path`, `benign_path`, `inputs_path`, `outputs_path`, `jailbreak_path`, `responses_path`, ...) move one file; `taxonomy_dir`/`prompt_dir` relocate config and prompt inputs.

## Key Design Decisions

- **Prompts are external** — no prompt text in library code; the stages' run-time additions sit in `content_moderation/feedback.py`. A new category is a taxonomy entry.
- **A dataset type is a file** — `dataset_type` (`training` or `eval`, no other) names `configs/dataset_types/<type>.json`, the defaults of a run of that type; every key resolves packaged default → type file → recipe → params file, and a `config_dir` overlays the type, taxonomy, augmentation, generation axes and dimensions files one by one. No code branches on the type but the build's mode.
- **Backends are swappable** — switching from API to vLLM is a recipe's `backend_type`, not a code change.
- **Inputs are per-category** — input samples land in `Datasets/constitution_inputs/{category}/samples.csv`. The other stages write their CSVs under `Datasets/` (one per paraphrase target and per jailbreak kind), and the constitution under `Data_cache/constitution/`. Merging is explicit (`build_dataset`): it takes the accepted rows of every stage (`accepted_mask`) and leaves out a row whose `sample_id` an earlier part of its file wrote; an eval build maps them onto three flat files. A training build also leaves out a benign or dual-use benign variation whose `technique` (`+`-joined) holds one the natural kind does not draw (`stages._NaturalVariations`, the variations `Part`'s `where`; a harmful-labelled row stays), with one WARNING naming the count and the techniques, and no count of its own in the run record. Rejected and error rows stay in the stage files. The jailbreak and variation rows of both builds gain `families` and `layers` (`stages._TechniqueTags`, `jailbreak.pool.chain_tags`): the first family and the layer of each technique of `technique`, `+`-joined in its order, read through the registry of every technique (a retired one keeps its family); a name the registry lacks gives `?<name>` and `?` and never stops the build (an INFO line names them with `verbose`), and the identity combination gives empty cells. They follow the jailbreak file's columns in `complete_dataset.csv` and `technique` in `eval_jailbreaks.csv`, empty on every other row; the stage files do not carry them.
- **Checker reasoning feeds back to the generator** — a rejection's reasoning goes into the next generation call (`checked()`, the outputs stage's `max_attempts`), and so does the length floor's reason (`precheck`).
- **Reject over accept** — a reply with the wrong count or format is rejected whole and asked again, never salvaged.
- **`Data_cache/` is internal** — the constitution and the benign pairs go there, never in `Datasets/`.
- **Resume model — one sidecar system** — every batched stage plans and resumes through the same two files, built on `redact.dataset.JsonlSidecar`: a `<artifact>.manifest.jsonl` **plan** (`Manifest`, one row per unit, written whole before generation) and a `<artifact>.state.jsonl` **ledger** (`Ledger`, one record per finished unit). Both key on the same per-stage unit id: constitution `source_category::prompt` (the entry type, or `general_benign`); inputs `(sample_description, entry_type, iteration)`; outputs `(input_id, iteration)`; paraphrase inputs / jailbreaks / variations / conversations `(input_id, iteration)`; paraphrase outputs `(response_id, iteration)`; the benign data `(main_category, sub_category, answer_type)`; conversation scoring `sample_id` (ledger only).
  - **A save** is two synced appends (`commit` / `CommitBuffer`): the rows of the finished units with `append_rows`, then their acks, the last carrying `_saved` (the size and a CRC32 of the last 4 kB of every file of the stage). A unit is acked only once its rows are on disk; a new ledger opens with an empty `_saved` line.
  - **A resume takes the finished units from the ledger alone.** `resume_state(ledger, resume=True, artifact=...)` takes the stage's lock (`<ledger name>.lock`, `filelock`), checks each output file against the recorded size and checksum (missing, shorter or different raises a `RuntimeError` naming the remedies), cuts off what an unfinished save left (kept in `<file>.cut`), cuts the ledger back to its last `_saved` line, and returns the finished keys; those units' rows are never written twice; a paraphrase unit under `min_words` words is acked `skipped` without a call, and stays skipped on resume. A folder written before the ledger recorded sizes is taken over once. Each save checks that every file still has its recorded size, so a second writer is caught.
  - **A fresh run** (`resume=False`) removes the output, its `.cut` and `.tmp` files, the ledger and the manifest, then plans anew; `clear_stage` does the same for a stage skipped for want of accepted rows. A stage of several files names their folder and pattern (inputs: `artifact=folder, pattern="*/samples.csv"`, a fresh run removing the whole tree); the constitution names its folder and `*.csv`.
  - **The jailbreak stage** keeps its manifest on a resume (its plan is sampled) and keeps beside it `<kind>.plan.json` (what the plan was made with; a resume with another section or seed raises, a pool that differs only by techniques the library added or retired after the plan's `spec_version`, or another `spec_version` or `rules`, warns and keeps the plan) and `<kind>.coverage.csv`, and writes `<kind>.variants.csv` there after each run from the rows (and, with `scenarios` on, appends `<kind>.scenarios.csv` in each save, kept to the rows after the run); the other stages write their manifest again from their inputs. The inputs and outputs stages deal their axes (the outputs also their answer modes) again on every run, a done unit keeping the spec (and mode) its ack records, and keep beside the manifest `<stem>.plan.json` (`seed`, the weights, and `samples_per_entry` for the inputs, `outputs_per_input` and `modes` for the outputs; a resume with others raises, the inputs' once the folder has a done unit) and `<stem>.coverage.csv`. `Manifest.write`, `write_plan` and `write_concat` write through `<file>.tmp`, synced, then a rename; a plan file that holds no record (an earlier version's, cut off) stops a resume, naming the remedies, with the lock given back. The driver adds `<stage>.run.json` per stage and one trace per run.
  - A failed batch **dispatch** propagates (the transport failing, never acked rows); only a unit's own exception, and on the async lane its `PromptTooLongError`, is isolated. When adding a stage, use `Manifest`, `Ledger`, `resume_state` and `CommitBuffer`; don't hand-roll `*.jsonl` read/write.
- **Concurrency is capability-driven, and settled at construction** — a backend binds `max_workers` from its setup's `recommended_max_workers` (or the run's `workers`), clamped against its class's `supports_parallel_calls`; `ModelClient` picks the dispatch of `generate()` once from `supports_native_batching`; `drive_units` sends a request on the async lane exactly when its backend has `supports_async_calls`. Overriding concurrency on a backend that can't support it raises.
- **Every dataset row has a `sample_id`** (its own content hash) **and, where it has an origin row, an `input_id`** (that row's `sample_id`): an input is the root (no `input_id`); output, jailbreak, variation, paraphrase and conversation rows carry both, and a paraphrase of a response also `response_id` (the response's `sample_id`; its `input_id` is the input answered). A jailbreak's `sample_id` is `content_id` of its text (`units.row_of`), so every technique and iteration variant has its own and an accepted no-op equals its input's (the build leaves it out); an error row's is `content_id("{label}:{input_id}:{iteration}")`; an outputs row of a prompt too long `content_id("{input_id}:{iteration}:prompt too long")`; a conversation's is `content_id("{input_id}:{iteration}")`. Constitution entries get `content_id(sample_description)`. When adding a stage, give every row a `sample_id`; add `input_id` only when there is an origin row.
- **Internals capture is a non-interfering hook, never a CSV column** — it writes only under `{log_dir}/...` and never touches a stage's rows, ledger or manifest. `internals_id(s)` is an explicit parameter of the calls that carry it (`LLMBackend.generate`/`agenerate`, `ModelClient`, `BatchCaller`, the router's batch helpers, `checked`/`extracted`, `LLMRequest`), never passed through `**kwargs`; only `TransformersIntrospectionBackend` acts on it, and `ModelClient`/`BatchCaller` raise `ValueError` before dispatch when a backend without `supports_internals` gets ids. Ids are rooted at an id the stage already has: outputs `{input_id}/{iteration}/output` and `/val_out` (later attempts under `/attempt_<n>`); inputs `<entry content id>/<iteration>/input` (the content id of `<sample_description>:<entry_type>`) and `<sample_id>/val_in` (every call asks for one sample); paraphrase `{input_id}/paraphrase/...` (`{response_id}/paraphrase/...` for the outputs target) and jailbreak `{input_id}/{label}/attempt_{iteration}`, captured under a provisional id and renamed to the row's `sample_id` (`rename_capture`). Conversations are not captured.
- **Telemetry is emitted low and decided high** — `llms/observe.py` is a bare hook, so `llms/` imports nothing upward and no optional dependency; `telemetry.py` owns sinks, aggregation and cost. A `call` event is one transport call (one per item for hosted models and vLLM). The JSONL trace is a plain file writer, never a `logging.Handler`; the library sets no log level and attaches no handler.
- **Cost is metered as it is bought** — tokens per *model* for APIs, engine wall-clock lifetime per *checkpoint* for local (two models sharing a load share one meter). Same principle as the caches: endpoint → SDK client, checkpoint → engine, model → rate-limit window.
- **A footprint is computed, not measured** — planning runs on `llms/resources/estimate.py` (shapes from the HF config, explicit headroom), since vLLM preallocates `gpu_memory_utilization × card` and its engine core runs in another process; `vram_gb` in the registry overrides the weights when known better. Everything is GiB.
- **src/ layout** — prevents accidental imports of local code during testing; the package installs with `pip install -e .`.

## Runner Scripts

A run is a recipe (plus its params file) handed to `run_pipeline`, or to `scripts/run.py RECIPE [--params P] [--data-dir D] [--quiet|--debug]`, which configures logging and prints the summary; `src/redact/configs/runs/` holds an eval and a training example, each with its params file (`params_eval_example.json` sets no `build.exclude_from`, since the training run's folder may not exist; its `_comment` says what to add). Each stage logs its acceptance counts and leaves a `{stage}.run.json` record; `scripts/inspect_run.py DATA_DIR` prints them. `scripts/scaffold_prompts.py TARGET [--empty] [--overwrite]` writes an editable prompt overlay (a file the folder holds stops it before it writes any, unless `--overwrite`; `scaffold_prompt_tree(..., overwrite=False)` raises `FileExistsError`); `scripts/scaffold_setup.py TARGET [--overwrite]` a setup folder of recipes and the configs a `config_dir` overlays; `scripts/download_models.py [MODELS] [--dry-run]` fetches the local checkpoints of the registry, whole (tokenizer files included, GGUF files left out), at the revision an entry pins (two pins of one checkpoint stop it), plus the tokenizer files of a setup whose tokenizer vLLM loads from elsewhere (a `tokenizer` repository, or a `tokenizer_revision` other than `revision`), ahead of a run (`--dry-run` needs no `huggingface_hub`), and GlotLID for a model with the `machine_translation` or `paraphraser` role (the role decides: a model named as the paraphraser without it brings none); `scripts/gpu_check_residency.py STEP [--root R]` runs the residency and engine-lifecycle checks on a Linux machine with two equal cards; `scripts/search_smoke.py --root R [--target T --judge J]` runs a small real-model combination search (counts only, no text) against a local target; `scripts/persona_smoke.py [-n N] [--model M] [--check-model C]` runs benign sentences through the persona and cognitive techniques on a real model and prints acceptance and discard counts by reason, no text; `scripts/langmix_smoke.py [--n N] [--gen-model M] [--families F ...]` does the same for the four language-mix families (a dialect on the translation role's model); `scripts/catalog.py [--out-dir D] [--check]` writes the technique catalog, `docs/catalog.json` and `docs/catalog.md`, from the code (as `python -m redact.jailbreak.catalog`).

Rejection rate is the primary quality signal. A sustained high rejection rate means either a bad prompt (improvable) or a model capability ceiling (not improvable): a weak checker rejects almost everything.

## Generation Strategy

Diversity comes from the constitution: each entry (a category, subcategory, severity and sample description) drives its own generation calls, from one template. Each entry is `samples_per_entry` units, each dealt a spec of the generation axes (length, register, writer, framing, directness, focus) evenly per `(category, entry_type)` group (log-weighted in a training run), an entry's siblings different on every axis none of whose values holds more than 1/k of the weight (at k = 3, `length` and `writer`, and with log weighting `register` and `framing`); each input gets `outputs_per_input` responses (2 in a training run), each dealt an answer mode its input's entry type allows (harmful or helpful: the prompt, the checker and the label; from two per input a borderline input gets one of each), then a spec of the response axes (length, format, register), siblings differing on every axis none of whose values weighs over 1/k (at k = 2, every packaged one). The axes vary only what no augmentation family varies (`dimensions.json`, checked at run start). No earlier sample enters a generation prompt, so a prompt does not change as the run saves texts; a text is written once per folder, an exact repeat dropped after generation. The jailbreak plan deals layers, families and each family's techniques evenly per `(category, entry_type, iteration)` group, and the natural kind adds mild variations of the same inputs.

## Reference Implementations

Four reference projects informed this architecture, in `../reference_files/` relative to this repo, in order of influence:

1. **Jailbreak library** (`../reference_files/BELLS_Jailbreak_Test/`) — LLM call wrappers, rate limiting, retry logic, regex utilities, dataset splitting getters, runner script structure.
2. **Content moderation output** (`../reference_files/output dataset/`) — the vLLM integration pattern; the paraphrasing / fingerprint removal call pattern (its training pipeline is out of scope here).
3. **Content moderation input** (`../reference_files/input dataset/`) — the original generation + filtering flow; its hosting code is obsolete.
4. **Constitutional classifier** (`../reference_files/constitutional_classifier/`) — `constitution_gen.ipynb` and `constitution.csv`, the origin of `constitution/`.

## Out of Scope (Separate Repositories)

- **Defingerprinting pipeline** — reverse paraphraser training, the fingerprint removal model, the finetuning loop. This library calls a paraphraser model (the `paraphraser` role) but does not train one.
- **Prompt finetuner / auto-optimizer** — automated prompt optimization (task-dataset generation, running the task, feedback), reading and writing prompt JSONs in this library's schema.

## Public Release Notes

Prompts and template files ship with the library (`prompts/`, `configs/`); there is no redaction step. To change a prompt, overlay it: `scripts/scaffold_prompts.py TARGET_DIR` writes an editable copy of `prompts/` (`--empty` for TODO skeletons; it refuses to write over a file the folder holds unless `--overwrite`), and `prompt_dir=TARGET_DIR` reads each prompt from there when present. `Datasets/`, `Data_cache/` and `.env` are gitignored and in neither the wheel nor the sdist, so a release carries no run output and no key.
